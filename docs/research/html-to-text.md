# Rendering HTML mail as text

Research for ticket 05 (`.scratch/triage-tui/issues/05-html-to-text.md`), 2026-10-14. Question: which crate and approach should blorp (a Rust ratatui TUI) use to render HTML email bodies as text in the reading pane. Candidates compared: html2text, htmd, nanohtml2text, mail-parser's built-in `html_to_text`, ammonia plus a custom walker, and dom_smoothie. Criteria: width-aware wrapping and re-wrap on resize, link rendering (inline or footnotes), tables, images and tracking pixels, quoted-reply collapsing, HTML sanitising, and performance on large newsletters. The ticket also asks how meli and aerc render HTML and when JMAP makes conversion necessary at all.

Sources are the published crate sources downloaded from crates.io (html2text 0.17.3, htmd 0.5.5, nanohtml2text 0.3.0, mail-parser 0.11.9, ammonia 4.2.3, dom_smoothie 0.18.2), the crates.io and GitHub APIs, RFC 8621, the meli repository at commit [1ada94c](https://github.com/meli/meli/tree/1ada94c384bb6196ac163fded7af7c1177e120d4) (`meli/Cargo.toml` says version 0.9.0), the aerc repository at commit [0a43480](https://git.sr.ht/~rjarry/aerc/tree/0a43480356a0d846917e505fed2e381289561b89) (the GNUmakefile's fallback version is 0.22.0), the w3m manual and source on the tats/w3m master branch as fetched today, mailgun's talon source for the HTML quote markers that real clients emit, ratatui's docs.rs pages and main-branch source, and a benchmark written for this ticket and run on an Apple M2 Pro with rustc 1.98.0 in release mode. Line references for crates point at the docs.rs source browser for the exact published version.

## When conversion is needed at all

RFC 8621 defines two body part lists on the Email object. `textBody` is "A list of "text/plain", "text/html", "image/*", "audio/*", and/or "video/*" parts to display (sequentially) as the message body, with a preference for "text/plain" when alternative versions are available", and `htmlBody` is the same list "with a preference for "text/html" when alternative versions are available" ([RFC 8621 section 4.1.4](https://www.rfc-editor.org/rfc/rfc8621.html#section-4.1.4)). The part contents arrive in `bodyValues`, "a map of "partId" to an EmailBodyValue object for none, some, or all "text/*" parts", where `value` is "The value of the body part after decoding Content-Transfer-Encoding and the Content-Type charset, if both known to the server, and with any CRLF replaced with a single LF", with `isEncodingProblem` and `isTruncated` flags. So the server does charset decoding and transfer decoding; the client receives a Unicode string and never touches MIME.

Email/get selects which values to fetch: `fetchTextBodyValues` ("If true, the "bodyValues" property includes any "text/*" part in the "textBody" property"), `fetchHTMLBodyValues` (the same for `htmlBody`), `fetchAllBodyValues` (every text part in `bodyStructure`), and `maxBodyValueBytes`, which truncates each value to that many octets, "MUST ensure the truncation results in valid UTF-8", and for `text/html` "SHOULD NOT truncate inside an HTML tag" ([RFC 8621 section 4.2](https://www.rfc-editor.org/rfc/rfc8621.html#section-4.2)). `bodyProperties` defaults to `partId`, `blobId`, `size`, `name`, `type`, `charset`, `disposition`, `cid`, `language`, `location`, so `type` is always available on each part.

The RFC says "The exact algorithm for decomposing bodyStructure into textBody, htmlBody, and attachments part lists is not mandated" and gives a suggested JavaScript algorithm. In that algorithm a `multipart/alternative` with both representations puts `text/plain` into `textBody` and `text/html` into `htmlBody`; when only one representation exists ("Found HTML part only" or "Found plaintext part only") the missing list is filled from the other ([RFC 8621 section 4.1.4](https://www.rfc-editor.org/rfc/rfc8621.html#section-4.1.4)). The consequence for blorp: `textBody` can contain `text/html` parts. A message that is HTML-only has the same part in both lists. Conversion is needed exactly when the part the client decides to show has `type` `text/html`; it is never needed for `text/plain` parts.

`preview` is "A plaintext fragment of the message body" that "MUST NOT be more than 256 characters in length"; the server "may choose which part of the message to include in the preview; skipping quoted sections and salutations and collapsing white space can result in a more useful preview" ([RFC 8621 section 4.1.4](https://www.rfc-editor.org/rfc/rfc8621.html#section-4.1.4)). It is server-computed, needs no conversion, and is the right thing for the queue list; it is not a substitute for the reading pane.

Recommended fetch: request `textBody`, `htmlBody` and `bodyValues` with `fetchTextBodyValues: true` and `fetchHTMLBodyValues: true` in one Email/get. Show the `textBody` parts when every part in `textBody` is `text/plain` (or when `textBody` and `htmlBody` differ, which means a real alternative exists); otherwise convert the `text/html` parts. Fetching both costs one extra body string per message and avoids a second round trip when the user wants to switch between the text and HTML versions. A `maxBodyValueBytes` cap (for example 2 MiB) bounds memory and conversion time per message; the truncated HTML still parses because html5ever recovers from unbalanced markup.

For comparison, aerc's JMAP worker never uses `bodyValues`: its `bodyProperties` list is the structural fields only and `handleFetchMessageBodyPart` downloads each part's blob by `blobId` and decodes it locally ([worker/jmap/fetch.go L17-41, L157-194](https://git.sr.ht/~rjarry/aerc/tree/0a43480356a0d846917e505fed2e381289561b89/item/worker/jmap/fetch.go)). That fits aerc's backend-agnostic MIME pipeline; blorp has no such pipeline and should take the decoded strings the server offers.

## How meli and aerc render HTML

Neither client converts HTML in-process. Both pipe the HTML to an external w3m.

meli: when a part's content type is `text/html`, the viewer decodes it and runs the configured `pager.html_filter` through `sh -c`, defaulting to `w3m -I utf-8 -T text/html -o display_link_number=1`, writing the HTML to the filter's stdin and reading its stdout ([meli/src/mail/view/envelope.rs L148-162](https://github.com/meli/meli/blob/1ada94c384bb6196ac163fded7af7c1177e120d4/meli/src/mail/view/envelope.rs#L148-L162), [meli/src/mail/view/filters.rs L291-306](https://github.com/meli/meli/blob/1ada94c384bb6196ac163fded7af7c1177e120d4/meli/src/mail/view/filters.rs#L291-L306)). The documentation says the same: "By default meli tries to render HTML e-mail with w3m" and "The HTML of the e-mail is piped into html_filter's standard input" ([meli/docs/external-tools.md L107-115](https://github.com/meli/meli/blob/1ada94c384bb6196ac163fded7af7c1177e120d4/meli/docs/external-tools.md#L107-L115)). No `-cols` is passed, so the dump is wrapped at w3m's default: `DEFAULT_COLS` is 80 ([fm.h L107](https://github.com/tats/w3m/blob/master/fm.h#L107)) and `main.c` sets `COLS = DEFAULT_COLS` when dumping with no explicit width ([main.c L881-884](https://github.com/tats/w3m/blob/master/main.c#L881-L884)). The pager then re-wraps with `split_long_lines` ("Split long lines that would overflow on the x axis", default true) and `minimum_width` (default 80) ([meli.conf.5 L1730-1775](https://github.com/meli/meli/blob/1ada94c384bb6196ac163fded7af7c1177e120d4/meli/docs/meli.conf.5#L1730-L1775)). `display_link_number=1` makes w3m number links and append a numbered URL list, the same footnote style html2text produces ([w3m.1 L255-258](https://github.com/tats/w3m/blob/master/doc/w3m.1#L255-L258)). `auto_choose_multipart_alternative` (default true) picks the HTML alternative when the text alternative is empty (same section of meli.conf.5). melib has no HTML-to-text code of its own; a search of the tree for `w3m`, `html2text` and `html_filter` finds only the viewer, the configuration, the docs and the mailcap fixtures.

aerc: the default filter table maps `text/html=! html` with `pandoc -f html -t plain | colorize` and a bare `w3m` invocation as commented alternatives ([config/aerc.conf L772-779](https://git.sr.ht/~rjarry/aerc/tree/0a43480356a0d846917e505fed2e381289561b89/item/config/aerc.conf#L772-L779)). The `!` prefix runs the filter as the main process in aerc's embedded terminal with the TTY as stdin and stdout, so the filter "is expected to implement its own paging" ([doc/aerc-config.5.scd L1168-1173](https://git.sr.ht/~rjarry/aerc/tree/0a43480356a0d846917e505fed2e381289561b89/item/doc/aerc-config.5.scd#L1168-L1173)). The shipped `html` filter is a shell script around w3m: `-I UTF-8 -O UTF-8 -T text/html -s -graph -o fold_textarea=true -o fold_line=true -o decode_url=true -o display_link=true`; with a TTY it adds `display_borders=true` and inline images when w3m supports them; when piped it adds `-cols 100 -dump -o disable_center=true`. Unless the script is invoked as `html-unsafe` it also tries to block network access: `unshare --map-root-user --net` if available, else `socksify` with `SOCKS_SERVER=127.0.0.1:1`, else `use_proxy=true` with every proxy option set to `127.0.0.1:1`, to "prevent any phoning home by rendered emails" ([filters/html](https://git.sr.ht/~rjarry/aerc/tree/0a43480356a0d846917e505fed2e381289561b89/item/filters/html)). The viewer prefers alternatives in the order `alternatives=text/plain,text/html` ([config/aerc.conf L592-598](https://git.sr.ht/~rjarry/aerc/tree/0a43480356a0d846917e505fed2e381289561b89/item/config/aerc.conf#L592-L598)). The `colorize` filter styles quote depth with `quote_1` to `quote_4` and `quote_x` ([filters/colorize.c L175-201](https://git.sr.ht/~rjarry/aerc/tree/0a43480356a0d846917e505fed2e381289561b89/item/filters/colorize.c#L175-L201)) and the `wrap` filter is a C program whose usage line reads "Wrap text without messing up email quotes", default margin 80 ([filters/wrap.c](https://git.sr.ht/~rjarry/aerc/tree/0a43480356a0d846917e505fed2e381289561b89/item/filters/wrap.c)). Neither aerc nor meli collapses quoted replies.

Two lessons carry over. First, a renderer that can fetch remote resources is a tracking risk serious enough that aerc builds a network sandbox around it; an in-process converter with no HTTP dependency removes that risk entirely. Second, both clients render at a fixed column count (80 or 100) and then let the pager fold or split, which is what a user sees as ragged output on wide or narrow terminals; an in-process converter can render at the pane's real width and re-render on resize.

## html2text 0.17.3

Repository [jugglerchris/rust-html2text](https://github.com/jugglerchris/rust-html2text). crates.io: 0.17.3 published 2026-10-12, 6,562,252 total downloads, 1,684,173 in the last 90 days; licence MIT; `rust-version` 1.85, edition 2024 ([crates.io API](https://crates.io/api/v1/crates/html2text), [Cargo.toml](https://docs.rs/crate/html2text/0.17.3/source/Cargo.toml)). GitHub: 245 stars, 14 open issues, last push 2026-10-12 ([GitHub API](https://api.github.com/repos/jugglerchris/rust-html2text)). Dependencies are html5ever 0.40.1, tendril, thiserror and unicode-width, with nom behind the `css` feature and xml5ever behind `xml`; there is no HTTP or network dependency ([Cargo.toml](https://docs.rs/crate/html2text/0.17.3/source/Cargo.toml)). The README states the goal: "The project aims to do a reasonable job of rendering reasonable HTML in a terminal or other places where HTML needs to be converted to text (for example the text/plain fallback in HTML e-mails)" and parses with "the Servo project's HTML parser, html5ever" ([README](https://docs.rs/crate/html2text/0.17.3/source/README.md)). The maintainer wrote in 2024 "I have used html2text in my TUI email client from the start" ([issue #134, maintainer comment of 2024-02-23](https://github.com/jugglerchris/rust-html2text/issues/134)). The README also carries an AI policy: "this project is not able to accept code contributions produced with generative AI/LLMs" ([README](https://docs.rs/crate/html2text/0.17.3/source/README.md)), which matters if blorp ever needs to upstream a fix.

Pipeline and re-render. `Config::parse_html` produces an html5ever `RcDom`, `dom_to_render_tree` turns it into a `RenderTree`, and `render_to_string` or `render_to_lines` lay that tree out at a given width ([lib.rs L3130-3196](https://docs.rs/crate/html2text/0.17.3/source/src/lib.rs)). `RenderTree` derives `Clone` ([lib.rs L3469-3470](https://docs.rs/crate/html2text/0.17.3/source/src/lib.rs)), and the render methods take it by value, so the pattern for a resizable pane is: parse once, keep the tree, and on each width change call `render_to_lines(tree.clone(), width)`. The `render_to_lines` doc says "Take an existing RenderTree, and returns text wrapped to `width` columns. The text is returned as a `Vec<TaggedLine<_>>`; the annotations are vectors of the provided text decorator's `Annotation`" ([lib.rs L3178-3196](https://docs.rs/crate/html2text/0.17.3/source/src/lib.rs)). The shipped `html2term` example does this: it reads the terminal size and calls a `rerender` helper on the kept DOM for every redraw ([examples/html2term.rs L156-181](https://docs.rs/crate/html2text/0.17.3/source/examples/html2term.rs)).

Output types. A `TaggedLine<T>` is a sequence of `TaggedLineElement`, either a `TaggedString { s: String, tag: T }` or a zero-width `FragmentStart` marker ([text_renderer.rs L103-182](https://docs.rs/crate/html2text/0.17.3/source/src/render/text_renderer.rs)). With `config::rich()` the tag is `Vec<RichAnnotation>`, whose variants are `Default`, `Link(String)`, `Image(String)`, `Emphasis`, `Strong`, `Strikeout`, `Code`, `Preformat(bool)`, `Colour`, `BgColour` ([text_renderer.rs L2465-2487](https://docs.rs/crate/html2text/0.17.3/source/src/render/text_renderer.rs)). Each `TaggedString` maps directly onto a ratatui `Span` with a `Style` chosen from the annotations, and each `TaggedLine` onto a ratatui `Line`.

Wrapping. Wrapping is done inside the renderer using `unicode-width` for cell widths. Three options control it: `max_wrap_width` ("paragraphs will be wrapped to that width even if there is more total width available"), `min_wrap_width` (default 3), and `allow_width_overflow`, which returns output "wider than the specified width ... instead of returning `Err(TooNarrow)` if the output wouldn't otherwise fit" ([lib.rs L3254-3278](https://docs.rs/crate/html2text/0.17.3/source/src/lib.rs)). Without `allow_width_overflow`, rendering a deeply indented or table-heavy document into a narrow pane fails with `Error::TooNarrow` ([lib.rs L387-390, L3488](https://docs.rs/crate/html2text/0.17.3/source/src/lib.rs)); for a reading pane the overflow option plus horizontal scroll or truncation in ratatui is the right default. `no_link_wrapping` keeps link text on one line ([lib.rs L3298](https://docs.rs/crate/html2text/0.17.3/source/src/lib.rs)).

Links. Two mechanisms, independent of each other since 0.14.0 ("Link footnotes are now configurable independently of the decorator", [CHANGELOG](https://docs.rs/crate/html2text/0.17.3/source/CHANGELOG.md), [issue #193](https://github.com/jugglerchris/rust-html2text/issues/193)). The `PlainDecorator` writes `[` and `]` around link text ([text_renderer.rs L2303-2309](https://docs.rs/crate/html2text/0.17.3/source/src/render/text_renderer.rs)); `link_footnotes(true)` appends `[n]` references and the default `finalise` writes `[n]: url` lines at the end ([text_renderer.rs L938-945](https://docs.rs/crate/html2text/0.17.3/source/src/render/text_renderer.rs)). `config::plain()` enables decoration and footnotes; `config::rich()` and `with_decorator` start with `include_link_footnotes: false` ([lib.rs L3423-3458](https://docs.rs/crate/html2text/0.17.3/source/src/lib.rs)). With the rich decorator the URL travels as `RichAnnotation::Link(url)` on the span ([text_renderer.rs L2500-2502](https://docs.rs/crate/html2text/0.17.3/source/src/render/text_renderer.rs)), so the app can underline link text, collect the URLs per line for an "open link" picker, and still turn footnotes on with `link_footnotes(true)` if a numbered list is wanted.

Tables. The default renders tables with box-drawing borders and side-by-side cells; when a row does not fit, "the cells are drawn vertically instead of horizontally (because of space)" ([lib.rs L811-815](https://docs.rs/crate/html2text/0.17.3/source/src/lib.rs)). `raw_mode(true)` "traverses tables as if they had a single column and every cell is its own row" and implies `no_table_borders()`; `fence_tables()` wraps tables in triple backticks ([lib.rs L3281-3296](https://docs.rs/crate/html2text/0.17.3/source/src/lib.rs)). On the synthetic newsletter below, the default layout at 60 columns squeezes the 180-pixel image column to five cells and splits the alt text into `[[Ill`, `ustra`, `tion`, while `raw_mode` lays the same content out as readable stacked blocks. Newsletters are layout tables, so `raw_mode` is the better default for mail, with the bordered layout as a toggle for genuine data tables. The table layout code is also where the project's bug history lives: a hang on nested wide tables was fixed in 0.3.0 ([issue #54](https://github.com/jugglerchris/rust-html2text/issues/54)), 0.17.2 fixed "a divide by zero panic on `rowspan=0`", "panics related to some combinations of `rowspan`/`colspan`" and a "Stack overflow on destroying very nested render trees" ([CHANGELOG](https://docs.rs/crate/html2text/0.17.3/source/CHANGELOG.md), [issue #292](https://github.com/jugglerchris/rust-html2text/issues/292)), and [issue #282](https://github.com/jugglerchris/rust-html2text/issues/282) (open, 2026-07-26) reports that a cell holding stacked blocks gets the sum of their widths rather than the maximum, "very visible in the wild on HTML emails and newsletters, which nest a lot of stacked blocks inside layout tables" at large render widths. `raw_mode` sidesteps the column-width code entirely.

Images and tracking pixels. `<img>` without `src` is ignored; `alt` is used as the title ([lib.rs L2126-2149](https://docs.rs/crate/html2text/0.17.3/source/src/lib.rs)). `ImageRenderMode` defaults to `IgnoreEmpty`, which means "Ignore `<img>` without alt, or `<svg>` without `<title>`"; `ShowAlways`, `Replace(&str)` and `Filename` are the alternatives ([lib.rs L3006-3020](https://docs.rs/crate/html2text/0.17.3/source/src/lib.rs)). A tracking pixel has no alt text and so produces nothing; images with alt text render as `[alt]` with the plain decorator ([text_renderer.rs L2346-2348](https://docs.rs/crate/html2text/0.17.3/source/src/render/text_renderer.rs)) or as a span tagged `RichAnnotation::Image(src)`. Nothing is ever fetched: the crate has no network dependency, so the "phoning home" problem that aerc sandboxes against cannot occur. `<script>`, `<style>`, `<head>`, `<link>` and `<meta>` are dropped with their contents ([lib.rs L2063-2070](https://docs.rs/crate/html2text/0.17.3/source/src/lib.rs)).

Hidden preheader text. Marketing mail commonly puts a preview sentence in a `display:none` or `max-height:0; overflow:hidden` block. Without CSS support html2text shows it; with the `css` feature and `use_doc_css()`, "Rules with `display: none` will cause matching elements to be removed from the render tree. The same is true if `overflow: hidden` or `overflow-y: hidden` and the `height` or `max-height` are 0" ([README](https://docs.rs/crate/html2text/0.17.3/source/README.md)). That support was added for exactly this case ([issue #134](https://github.com/jugglerchris/rust-html2text/issues/134), released as 0.12.4). On the sample newsletter, `use_doc_css()` removes the preheader line and costs about 20 percent more render time (table below). The `css` feature adds `Colour`/`BgColour` annotations from document styles; blorp can ignore those annotations when mapping to ratatui styles.

Blockquotes. `<blockquote>` becomes a `BlockQuote` node ([lib.rs L2225](https://docs.rs/crate/html2text/0.17.3/source/src/lib.rs)) and the plain decorator's `quote_prefix` is `"> "` ([text_renderer.rs L2354-2356](https://docs.rs/crate/html2text/0.17.3/source/src/render/text_renderer.rs)), applied per nesting level, so a Gmail reply chain renders as `> ` and `> > ` lines (sample output below). `RichAnnotation` has no blockquote variant, so with the rich decorator the prefix text is the only signal of quote depth; the prefix is still emitted because it comes from the decorator's `quote_prefix`.

Performance. Measured below. The crate ships a `benches/tables.rs` that exercises nested tables, the historically slow case ([benches/tables.rs](https://docs.rs/crate/html2text/0.17.3/source/benches/tables.rs)).

## htmd 0.5.5

Repository [letmutex/htmd](https://github.com/letmutex/htmd). crates.io: 0.5.5 published 2026-07-27, 6,549,653 total downloads, 4,950,516 in the last 90 days; licence Apache-2.0 ([crates.io API](https://crates.io/api/v1/crates/htmd), [Cargo.toml](https://docs.rs/crate/htmd/0.5.5/source/Cargo.toml)). GitHub: 459 stars, 3 open issues, last push 2026-10-13 ([GitHub API](https://api.github.com/repos/letmutex/htmd)). It is "An HTML to Markdown converter for Rust, inspired by turndown.js", built on html5ever only, and its bench README reports 14.5 ms to convert a 1.37 MB Wikipedia page on an Apple M4 ([README](https://docs.rs/crate/htmd/0.5.5/source/README.md), [benches/README.md](https://docs.rs/crate/htmd/0.5.5/source/benches/README.md)).

It produces Markdown, not wrapped text. There is no width parameter anywhere in the API (`Options` covers heading, hr, br, link, code block, bullet and translation styles, [options.rs](https://docs.rs/crate/htmd/0.5.5/source/src/options.rs)); on the sample newsletter its longest output line is 345 characters. Links are `Inlined`, `InlinedPreferAutolinks` or `Referenced` with `Full`, `Collapsed` or `Shortcut` reference styles ([options.rs L85-99](https://docs.rs/crate/htmd/0.5.5/source/src/options.rs)). Tables become pipe tables only when the table has explicit header cells and is not nested inside another table cell; otherwise the handler falls back to rendering the cells as ordinary blocks ([element_handler/table.rs L18-24](https://docs.rs/crate/htmd/0.5.5/source/src/element_handler/table.rs)), which is the right fallback for layout tables. Two defaults are wrong for mail: `script` and `style` are in the generic block handler list, not skipped ([element_handler/mod.rs L212-230](https://docs.rs/crate/htmd/0.5.5/source/src/element_handler/mod.rs)), so the newsletter's `<style>` sheet appears as a paragraph of CSS unless `skip_tags(vec!["script", "style"])` is set, which the README shows as a separate step; and the image handler emits every `<img>` with a `src` as `![alt](src)`, including the tracking pixel as `![](https://track.example.test/open?id=abc123)` ([element_handler/img.rs](https://docs.rs/crate/htmd/0.5.5/source/src/element_handler/img.rs)). Using htmd would mean adding a Markdown-to-ratatui layer that wraps, styles and resolves links; that layer is the hard part of the problem and htmd does none of it. It is a good tool for turning web pages into Markdown and the wrong shape for a reading pane.

html2md 0.2.17 and fast_html2md 0.0.63 are the same category (HTML to Markdown) and were not evaluated further ([crates.io API](https://crates.io/api/v1/crates/html2md), [crates.io API](https://crates.io/api/v1/crates/fast_html2md)).

## nanohtml2text 0.3.0

Repository [alexwennerberg/nanohtml2text](https://github.com/alexwennerberg/nanohtml2text). crates.io: 0.3.0 published 2026-08-27, 517,330 total downloads, 174,856 in the last 90 days; licence MIT; no dependencies ([crates.io API](https://crates.io/api/v1/crates/nanohtml2text), [Cargo.toml](https://docs.rs/crate/nanohtml2text/0.3.0/source/Cargo.toml)). GitHub: 0 stars, 0 open issues, last push 2026-08-27 ([GitHub API](https://api.github.com/repos/alexwennerberg/nanohtml2text)). The README describes it as a "0-dependency library to convert HTML to text; an alternative to html2text that doesn't use a full browser-grade HTML parser", "Primarily useful for displaying HTML emails as text. YMMV depending on the structure of the HTML you're trying to convert", with one function, `html2text(&str) -> String` ([README](https://docs.rs/crate/nanohtml2text/0.3.0/source/README.md)).

It is a hand-written tag scanner in 781 lines. Links render inline as `text (href)` when the text differs from the URL, with `javascript:` URLs dropped ([lib.rs L392-416](https://docs.rs/crate/nanohtml2text/0.3.0/source/src/lib.rs)); `br`, `li`, `tr`, `td`, `th` produce one line break and `p`, `div`, headings, `blockquote` and the sectioning elements two ([lib.rs L418-428](https://docs.rs/crate/nanohtml2text/0.3.0/source/src/lib.rs)); `head`, `script`, `style`, `template` and `title` are skipped with their contents ([lib.rs L447-465](https://docs.rs/crate/nanohtml2text/0.3.0/source/src/lib.rs)); `img` becomes its alt text or nothing ([lib.rs L467](https://docs.rs/crate/nanohtml2text/0.3.0/source/src/lib.rs)). There is no wrapping (longest sample line 338 characters), no quote prefix (the reply chain renders with every level flush left), no annotations to style from, and no table layout. It is the fastest candidate and a reasonable fallback or fuzz-comparison tool, not a reading-pane renderer.

## mail-parser 0.11.9 `html_to_text`

mail-parser (Stalwart, Apache-2.0 OR MIT, 0.11.9 published 2026-09-09, [crates.io API](https://crates.io/api/v1/crates/mail-parser)) exposes `mail_parser::decoders::html::html_to_text(&str) -> String`, a byte scanner that tracks `in_head`, `in_style`, `in_script`, `in_template` and `in_comment` and inserts a newline only for `<br>` and closing `</p>` ([decoders/html.rs L38-95](https://docs.rs/crate/mail-parser/0.11.9/source/src/decoders/html.rs)). Every other block boundary collapses into a space: the 38-item sample newsletter comes out as 79 lines with a 509-character longest line, and the reply-chain sample's signature, cite block and Outlook header all land on one line. Links are dropped. It exists so a MIME parser can produce a `text/plain` fallback for indexing; it is not a renderer. blorp does not need mail-parser anyway, since JMAP delivers decoded body values.

## ammonia 4.2.3 plus a custom walker

ammonia (MIT OR Apache-2.0, 4.2.3 published 2026-10-11, 680 stars, [crates.io API](https://crates.io/api/v1/crates/ammonia), [GitHub API](https://api.github.com/repos/rust-ammonia/ammonia)) "is a whitelist-based HTML sanitization library. It is designed to prevent cross-site scripting, layout breaking, and clickjacking caused by untrusted user-provided HTML being mixed into a larger web page" and "parses its input exactly according to the HTML5 specification; it will not linkify bare URLs, insert line or paragraph breaks" ([lib.rs L7-16](https://docs.rs/crate/ammonia/4.2.3/source/src/lib.rs)). Its output is HTML. Building on it would mean writing the walker, the block model, the wrapper, the table and list layout and the link bookkeeping from scratch, which is html2text's roughly 9,800 lines of non-test code again. The threats it defends against do not exist in a terminal: no script runs, no CSS lays anything out, and no element can be clicked. The remaining text-level threat, control characters and escape sequences smuggled into text, is handled on the ratatui side: `Buffer::set_stringn` "Skips zero-width graphemes and control characters" and filters graphemes with `!symbol.contains(char::is_control)` ([ratatui-core buffer.rs L332-351](https://github.com/ratatui/ratatui/blob/main/ratatui-core/src/buffer/buffer.rs#L332-L351)). Sanitising is therefore not a reason to add a crate. Where ammonia could still earn a place is as a cheap pre-pass that strips `<style>` and `<script>` content before a converter that does not (its documented `clean_content_tags` example removes both, [lib.rs L601-607](https://docs.rs/crate/ammonia/4.2.3/source/src/lib.rs)), but html2text already drops them, and the pre-pass costs about as much as html2text's own parse (table below).

## dom_smoothie 0.18.2

dom_smoothie (MIT, 0.18.2 published 2026-09-21, 224 stars, [crates.io API](https://crates.io/api/v1/crates/dom_smoothie), [GitHub API](https://api.github.com/repos/niklak/dom_smoothie)) "closely follows the implementation of readability.js", returning an `Article` with `content` (HTML) and `text_content`; the README's own example says "`text_content` provides almost the same result as readability.js, which is far from perfect. It may squash words together if element nodes don't have a whitespace before closing" ([README](https://docs.rs/crate/dom_smoothie/0.18.2/source/README.md), [readability.rs L22-47](https://docs.rs/crate/dom_smoothie/0.18.2/source/src/readability.rs)). Readability's job is to guess which part of a web page is the article and discard the rest; applied to mail it would drop headers, footers, unsubscribe links and short replies by design. It is a content extractor, not a renderer, and its text output is explicitly not layout-aware. Not suitable.

## Quoted-reply collapsing

No candidate crate detects quoted replies; this is app logic over the rendered lines. Real clients mark quotes in a handful of ways, catalogued by the selectors in mailgun's talon, which exists to strip them: Gmail wraps the quote in an element with class `gmail_quote`, Yahoo uses class `yahoo_quoted`, Outlook emits a `div` whose `style` is `border:none;border-top:solid #E1E1E1 1.0pt;padding:3.0pt ...` or an element with id `divRplyFwdMsg`, older Outlook uses id `OLK_SRC_BODY_SECTION`, Zimbra uses `hr[data-marker="__DIVIDER__"]`, and the generic fallback is the outermost `blockquote` ([talon/html_quotations.py L20, L222-236, L250-290, L324-330, L415-417](https://github.com/mailgun/talon/blob/master/talon/html_quotations.py); the order of attempts is in [talon/quotations.py L552-559](https://github.com/mailgun/talon/blob/master/talon/quotations.py#L552-L559)). Apple Mail uses `<blockquote type="cite">`, which the generic blockquote rule covers.

Because html2text renders every `blockquote` with a `> ` prefix per level, the cheapest collapsing that works for both HTML-derived and plain-text bodies is line-based: after rendering, fold each maximal run of lines whose text starts with `>` into a single placeholder such as `[12 quoted lines]`, expandable with a key. Plain-text replies already use `>` by convention, and aerc's `colorize` relies on the same convention for its quote colours. A second, optional layer uses the class markers: with the `css` feature, `Config::add_css(".gmail_quote { display: none }")` (and a matching rule for `.yahoo_quoted`) removes those containers before rendering, since html2text's CSS support covers "Basic selector matching (including child and descendents, classes and element types)" and `display: none` removal ([README](https://docs.rs/crate/html2text/0.17.3/source/README.md)). That hides rather than folds, so it should be the "hide quotes" toggle rather than the default. The Outlook style-attribute and id markers need a DOM pass; html2text exposes the `RcDom` from `parse_html` before `dom_to_render_tree`, so a small walker could strip or tag those nodes if it proves worth it. Not for v1.

## Performance

Benchmark: a generator produced three synthetic newsletters in common marketing-mail markup (a 600-pixel centred outer table, nested two- and three-column row tables, inline styles, a `<style>` block, a `display:none` preheader, an image and two links per item, a call-to-action button table, a data table every ten items, and two 1x1 tracking pixels) at 67,737 bytes (38 items), 341,935 bytes (190 items) and 1,360,823 bytes (758 items), plus a Gmail-style three-deep reply chain for the quote output. Each converter ran seven times per input in a release build on an Apple M2 Pro with rustc 1.98.0; the table shows the median. html2text was compiled with the `css` feature. The generator and harness are not committed; the numbers are reproducible from the description.

| Converter and mode | 68 KB | 342 KB | 1.36 MB |
| --- | --- | --- | --- |
| html2text `plain()` full pipeline, width 80 | 4.0 ms | 16.9 ms | 70.6 ms |
| html2text parse to `RenderTree` only | 1.9 ms | 6.9 ms | 27.6 ms |
| html2text re-render kept tree, `rich()`, width 60 | 2.6 ms | 10.1 ms | 43.0 ms |
| html2text re-render kept tree, `rich()`, width 100 | 2.3 ms | 10.6 ms | 43.3 ms |
| html2text re-render kept tree, `rich()`, width 160 | 2.2 ms | 11.1 ms | 46.8 ms |
| html2text `plain()` with `raw_mode`, width 80 | 2.6 ms | 13.2 ms | 54.8 ms |
| html2text `raw_mode` plus `use_doc_css`, width 80 | 3.1 ms | 16.0 ms | 66.1 ms |
| htmd `convert` (Markdown, unwrapped) | 1.4 ms | 6.5 ms | 26.2 ms |
| nanohtml2text | 0.3 ms | 1.4 ms | 5.6 ms |
| mail-parser `html_to_text` | 0.2 ms | 0.9 ms | 3.6 ms |
| ammonia `clean` (sanitise only, output is HTML) | 1.3 ms | 6.5 ms | 25.9 ms |

Reading of the numbers: a typical newsletter (tens to a few hundred kilobytes) converts in single-digit to low-double-digit milliseconds with html2text, and re-rendering a kept tree at a new width costs about 60 percent of a full conversion. A 1.4 MB newsletter, which is far above normal, takes 70 ms for the full pipeline and 43 ms per re-render. Scaling is linear across the three sizes for every converter. The faster converters are faster because they do less (no wrapping, no layout, no annotations); none of them removes the need for a wrapping layer, and ratatui's own word wrapper would then run on every frame rather than on resize. None of the measured cases hit the pathological table layouts in html2text's issue history, but those exist, so conversion should run off the UI thread with the `maxBodyValueBytes` cap bounding input size; a message that fails to render in a bounded time can fall back to nanohtml2text or the `textBody` alternative.

## Recommendation

Use html2text 0.17.3 with the `css` feature, in-process, with the rich decorator. The specific configuration: `config::rich().raw_mode(true).use_doc_css().allow_width_overflow()`, with `link_footnotes(true)` as a user toggle. Parse each message once when it is opened (`parse_html` then `dom_to_render_tree`), keep the `RenderTree`, and call `render_to_lines(tree.clone(), pane_width)` whenever the pane width changes; map each `TaggedString` to a ratatui `Span` using `Link`, `Emphasis`, `Strong`, `Strikeout`, `Code` and `Preformat` annotations and ignore `Colour`/`BgColour`; hand the resulting `Vec<Line>` to a `Paragraph` without ratatui wrapping, since the lines are already fitted. Keep the URL from each `Link` annotation alongside its line so an "open link" action can list the links on screen. Collapse quoted replies at the line level by folding runs of `>`-prefixed lines, which also covers plain-text bodies; offer a "hide quotes" toggle that adds the `gmail_quote`/`yahoo_quoted` CSS rule. Offer a "table layout" toggle that re-renders without `raw_mode` for data tables. Run conversion off the UI thread and fetch bodies with `maxBodyValueBytes` set, so a hostile or enormous message cannot stall the queue.

Reasons: it is the only candidate that solves wrapping, link bookkeeping, tables, image suppression and quote prefixes in one place, it ships annotations that map one-to-one onto ratatui spans, it never touches the network (which is what aerc builds a sandbox to prevent), its author runs it in a TUI mail client and has fixed every mail-specific report found in the tracker (preheaders, link footnotes, panics on malformed tables, stack overflows), and its cost on realistic newsletters is milliseconds. Its weak spot is the table layout engine, and `raw_mode` avoids it by default.

Decide between text and HTML per message from JMAP: fetch `textBody`, `htmlBody` and `bodyValues` with `fetchTextBodyValues` and `fetchHTMLBodyValues` both true, show the `text/plain` parts directly when a genuine alternative exists, and convert only `text/html` parts. Use `preview` for the queue row and never for the pane. Rejected: htmd (Markdown out, no wrapping, emits tracking pixels and stylesheets by default), nanohtml2text (no wrapping, no quote markers, no annotations; acceptable as a last-resort fallback), mail-parser's `html_to_text` (collapses block structure), ammonia plus a walker (solves a web problem the terminal does not have, and leaves the whole renderer to be written), and dom_smoothie (an article extractor that discards parts of a mail on purpose).
