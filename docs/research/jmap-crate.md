# JMAP crate choice

Research for ticket 02 (`.scratch/triage-tui/issues/02-jmap-crate.md`), 2026-10-14. Question: which Rust JMAP client should sift build on: jmap-client (Stalwart), io-jmap (Pimalaya), or hand-rolled reqwest plus serde. Criteria: adding the snooze capability and the `snoozed` Email property without forking; Thread and Email query and Email/changes with state strings; blob download via Fastmail's separate download host; push (EventSource or WebSocket); async model and fit with a ratatui event loop on tokio; maintenance cadence; licence.

Sources are the crate repositories at the commits named below (cloned and read, with one claim checked by compiling and running a probe against the jmap-client source), the crates.io and GitHub APIs, docs.rs, RFC 8620 and RFC 8621, the expired snooze draft, and Fastmail's developer page. Line references are to those commits: jmap-client at [f5556ff](https://github.com/stalwartlabs/jmap-client/tree/f5556ff521c6b5a76702bdca180014a726add3ff) (the 0.4.3 release commit) and io-jmap at [919eab4](https://github.com/pimalaya/io-jmap/tree/919eab465ab620b323f9191ab8de2f640bc4a1d2) (one commit after the v0.6.0 tag).

## What sift needs from the protocol

Snooze is specified by [draft-ietf-extra-email-snooze-00](https://datatracker.ietf.org/doc/html/draft-ietf-extra-email-snooze-00). The datatracker page for the draft says "This Internet-Draft is no longer active", lists revision 00 as the only revision (dated 2023-10-30), and shows the stream state as "Parked WG Document" ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-extra-email-snooze/)). The draft text says it "will expire on 25 April 2024". Its authors are Ken Murchison, Ricardo Signes and Neil Jenkins, all Fastmail staff at the time.

The draft defines a capability named `urn:ietf:params:jmap:mail:snooze` whose value "is an empty object in both the JMAP session "capabilities" property" and "an account's "accountCapabilities" property"; a mailbox role `snoozed` ("Users may create a mailbox with a role of "snoozed", having the sole purpose of holding snoozed emails"); and an Email property `snoozed: SnoozeDetails|null (immutable)` where SnoozeDetails has `until` (UTCDate, "The time at which to move the message out of the "snoozed" mailbox"), optional `moveToMailboxId` and optional `setKeywords` ([draft section on JMAP](https://datatracker.ietf.org/doc/html/draft-ietf-extra-email-snooze-00)). The IETF 117 slides by Jenkins and Murchison state the client-side procedure: to snooze, "Update the mailboxIds property of the email to include the id of the mailbox having the "snoozed" role" and "Set SnoozeDetails on the snoozed property on the email"; to unsnooze, remove that mailbox id and "Set the snoozed property on the email to null" ([slides-117-jmap-jmap-mail-snooze-00](https://datatracker.ietf.org/meeting/117/materials/slides-117-jmap-jmap-mail-snooze-00), slides 5 and 6). So a client library must let sift (a) put `urn:ietf:params:jmap:mail:snooze` in the request `using` list, (b) read `snoozed` from Email/get, and (c) write `snoozed` as an object in Email/set updates alongside a `mailboxIds` patch.

RFC 8620 defines `using` as "The set of capabilities the client wishes to use" and the request-level error `unknownCapability` as "The client included a capability in the "using" property of the request that the server does not support" ([RFC 8620 §3.3 and §3.6.1](https://www.rfc-editor.org/rfc/rfc8620.html#section-3.3)). A `/changes` call takes `sinceState` and returns `oldState`, `newState`, `hasMoreChanges` and the `cannotCalculateChanges` error ([RFC 8620 §5.2](https://www.rfc-editor.org/rfc/rfc8620.html#section-5.2)). The session's `downloadUrl` is a URI Template that "MUST contain variables called "accountId", "blobId", "type", and "name"", and the client fills it and makes "an authenticated GET request to the download URL" ([RFC 8620 §2 and §6.2](https://www.rfc-editor.org/rfc/rfc8620.html#section-6.2)). Push over Event Source is a `text/event-stream` resource whose URL template has `types`, `closeafter` and `ping` variables; the server pushes `state` events carrying a StateChange object (`changed`: account id to type name to state string) and, when `ping` is non-zero, `ping` events; a reconnecting client sends `Last-Event-ID` ([RFC 8620 §7.1 and §7.3](https://www.rfc-editor.org/rfc/rfc8620.html#section-7.3)). RFC 8621 makes Thread "a flat list of Emails, ordered by date" with `emailIds` "sorted by the "receivedAt" date of the Email, oldest first", gives Email/query a `collapseThreads` argument, and makes Email/changes a standard `/changes` method ([RFC 8621 §3, §4.3, §4.4](https://www.rfc-editor.org/rfc/rfc8621.html#section-4.4)).

Fastmail's developer page gives the session resource as `https://api.fastmail.com/jmap/session`, authenticated with an API token sent as `Authorization: Bearer {value}`, and lists the capability `https://www.fastmail.com/dev/maskedemail` alongside the standard core, mail, submission, vacationresponse and contacts URIs ([fastmail.com/dev](https://www.fastmail.com/dev/)). The page does not document snooze, the download host or push. A third-party capture of a Fastmail session object shows `apiUrl` `https://api.fastmail.com/jmap/api/`, `downloadUrl` `https://www.fastmailusercontent.com/jmap/download/{accountId}/{blobId}/{name}?type={type}`, `uploadUrl` `https://api.fastmail.com/jmap/upload/{accountId}/` and `eventSourceUrl` `https://api.fastmail.com/jmap/event/` ([demo-fastmail-api-jmap README](https://github.com/joelparkerhenderson/demo-fastmail-api-jmap)). That is not a Fastmail document; the live session object is the authority, and sift should read these URLs from it rather than hardcode them. The point that matters here is that downloads go to a different host from the API, and that `eventSourceUrl` as captured has no template variables, so a client must handle both the templated and the bare form.

## jmap-client (Stalwart)

Repository [stalwartlabs/jmap-client](https://github.com/stalwartlabs/jmap-client). crates.io: 0.4.3 published 2026-09-28; earlier releases 0.4.2 (2026-06-19), 0.4.1 (2026-04-13), 0.4.0 (2025-10-19), 0.3.3 (2025-09-29), then a gap back to 0.3.2 (2023-12-29); 88,840 total downloads, 25,941 in the last 90 days ([crates.io API](https://crates.io/api/v1/crates/jmap-client/versions)). Licence `Apache-2.0 OR MIT` ([Cargo.toml](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/Cargo.toml)); the 2025-09-29 "Updated license" commit only changed the copyright holder from "Stalwart Labs Ltd." to "Stalwart Labs LLC". GitHub: 123 stars, 13 open issues, last push 2026-09-28 ([GitHub API](https://api.github.com/repos/stalwartlabs/jmap-client)). CI is a single `cargo build` and `cargo test` job ([rust.yml](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/.github/workflows/rust.yml)); there is no `tests/` directory, so the suite is the in-crate unit tests. docs.rs reports 0.47% of items documented ([docs.rs](https://docs.rs/jmap-client/latest/jmap_client/)). Commits since 2024 are release bumps and dependency changes (rustls default backend, tokio-tungstenite, base64 to encodify); the 2026 issues #29 to #36 are all open with no maintainer fix.

Snooze without forking: not possible. The request `using` list is typed as `Vec<URI>` ([request.rs L50](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/core/request.rs#L50)) and `URI` is a closed enum of twelve variants with no catch-all ([lib.rs L210](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/lib.rs#L210)); a probe that deserialises `"urn:ietf:params:jmap:mail:snooze"` into `jmap_client::URI` fails with `unknown variant`. Method arguments are a closed untagged `Arguments` enum ([request.rs L70](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/core/request.rs#L70)), so there is no way to send a raw JSON method call either. On the read side, `Email<Get>` has a `#[serde(flatten)] headers: AHashMap<Header, Option<HeaderValue>>` field that absorbs every unrecognised key ([email/mod.rs L188](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/email/mod.rs#L188)); `Header::parse` returns `None` unless the key starts with `header:` ([email/mod.rs L573](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/email/mod.rs#L573)) and `HeaderVisitor` turns that into a deserialisation error ([L475](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/email/mod.rs#L475)). A probe compiled against the 0.4.3 source confirms it: deserialising an Email JSON with `"snoozed": null` fails with `Failed to parse JMAP header 'snoozed'`, and so does one with a SnoozeDetails object, while the same JSON without `snoozed` parses. `Property::Other(String)` exists ([L326](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/email/mod.rs#L326)), so the property can be requested, but the response then cannot be parsed. On the write side, `Email<Set>` only offers typed setters plus a `patch` map of `String` to `bool` for keyword and mailbox flags ([email/set.rs](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/email/set.rs)), so a `snoozed` object cannot be sent. Adding snooze means forking three places: the `URI` enum, the `Email` struct and its header-catch-all, and the set builder.

Fastmail compatibility has a second, independent problem. `Request::new` always sends eleven capabilities in `using`, including sieve, blob, quota, principals, calendars and websocket ([request.rs L477-491](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/core/request.rs#L477-L491)). Issue #32 ("bug: don't send all capabilities in requests", opened 2026-07-03, still open) reports that "Using this lib for fastmail is broken after 0.4.1 (I get some 400 errors)" and gives the workaround of overwriting `request.using` with core and mail before every send ([issue #32](https://github.com/stalwartlabs/jmap-client/issues/32)). The `using` field is public, so this is a per-request workaround rather than a fork, but every helper method (`email_query`, `email_get`, and so on) builds its own request and cannot be told to trim the list.

Thread and Email query, and changes: covered. `email_query` takes a `Filter` with `in_mailbox`, keyword and thread conditions and a comparator list, and the response exposes `query_state`, `position`, `total`, `can_calculate_changes` ([core/query.rs](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/core/query.rs), [email/query.rs](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/email/query.rs)). `email_changes(since_state)` returns `old_state`, `new_state`, `has_more_changes`, `created`, `updated`, `destroyed` ([core/changes.rs](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/core/changes.rs)). `thread_get` and `changes_thread` exist ([thread/helpers.rs](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/thread/helpers.rs)). Result references between batched calls are supported (the README example chains Mailbox/changes into Mailbox/get).

Blob download: `Client::download(blob_id)` expands the session's `downloadUrl` template with the account id and blob id, fills `name` with `none` and `type` with `application/octet-stream`, and issues a GET with a fresh reqwest client carrying the same default headers (bearer token included) ([blob/download.rs L23](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/blob/download.rs#L23)). Because it builds the URL from the template, a different host such as `www.fastmailusercontent.com` works without special handling. It builds a new `reqwest::Client` per call rather than reusing a pool.

Push: `Client::event_source(types, close_after_state, ping, last_event_id)` expands the `eventSourceUrl` template and returns a `futures::Stream` of `PushNotification` ([event_source/stream.rs L22](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/event_source/stream.rs#L22)). It does not reconnect; the stream ends on the first transport error. The SSE parser treats a comment line as a state transition back to `Init`, after which the blank line that ends a comment-only block emits an empty event ([parser.rs L153](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/event_source/parser.rs#L153)), and `filter_notification` then tries to JSON-decode the empty data. Issue #36 (opened 2026-10-06, open) reports exactly this against Fastmail, whose event source "sends a comment as the first block confirming the connection", so the stream "return[s] an `Err` immediately" ([issue #36](https://github.com/stalwartlabs/jmap-client/issues/36)). The `types` argument is a closed `DataType` enum ([lib.rs L341](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/lib.rs#L341)), and the StateChange map is keyed by that enum, so any type name Fastmail pushes that the enum lacks is a parse error; passing an explicit type list limits what the server pushes. WebSocket (RFC 8887) is behind the `websockets` feature with `connect_ws`, `send_ws` and `enable_push_ws` ([client_ws.rs](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/client_ws.rs)); the captured Fastmail session lists no `urn:ietf:params:jmap:websocket` capability, so that path is not useful for sift.

Async model: every client method is `async` via the `maybe_async` macro and the default `async` feature uses reqwest 0.13 on tokio; the `blocking` feature swaps in `reqwest::blocking` ([Cargo.toml](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/Cargo.toml), [client.rs L186](https://github.com/stalwartlabs/jmap-client/blob/f5556ff521c6b5a76702bdca180014a726add3ff/src/client.rs#L186)). This fits a tokio-driven ratatui loop directly: JMAP calls are futures that can be spawned and their results sent back over a channel. The crate pulls in reqwest, tokio-tungstenite, rustls with aws-lc-rs by default, and chrono; issue #34 notes that the rustls native-roots change "forces `aws-lc-rs` on every consumer" ([issue #34](https://github.com/stalwartlabs/jmap-client/issues/34)).

Licence `MIT OR Apache-2.0`, edition 2024 ([Cargo.toml](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/Cargo.toml)). GitHub: 2 stars, 0 open issues, last push 2026-10-10 ([GitHub API](https://api.github.com/repos/pimalaya/io-jmap)); 60 commits in total, the first on 2026-06-05, with a single author (soywod). CI runs the shared Pimalaya test workflow plus two live integration jobs, one against a Fastmail account from repository secrets and one against a local Stalwart ([tests.yml](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/.github/workflows/tests.yml)); the Fastmail test covers "import/query/get/update, thread fetch, blob upload, and cleanup" ([tests/fastmail.rs L23](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/tests/fastmail.rs#L23)) but not blob download or the event source. docs.rs reports 100% documented and the crate denies missing docs ([docs.rs](https://docs.rs/io-jmap/latest/io_jmap/), [lib.rs L2](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/lib.rs#L2)). The changelog records breaking changes in 0.4.0, 0.4.1, 0.5.0 and 0.6.0 and one more pending for the next release ([CHANGELOG.md](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/CHANGELOG.md)). Pimalaya is funded by NLnet grants through 2027 per the README, and its contributing guide points to an AI policy under which "Pimalaya projects are developed with AI assistance, mainly Claude Code" with the rule that every change is compiled, tested and checked against the RFC before commit ([AI_POLICY.md](https://github.com/pimalaya/.github/blob/master/AI_POLICY.md)).

Snooze without forking: possible, through the generic layer. `JmapRequest.using` is `Vec<String>` and `method_calls` is `Vec<(String, serde_json::Value, String)>` ([request.rs L28](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/rfc8620/request.rs#L28)), and `JmapBatch::add(method, Value)` plus `into_request(using)` builds any call. The generic `JmapGet::<T>::new(account_id, auth, api_url, method, capabilities, opts)` decodes into any `Deserialize` type ([get.rs L122](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/rfc8620/get.rs#L122)); `JmapSet::new<C: Serialize, U: Serialize>` takes arbitrary create and update payloads and a capability list ([set.rs L126](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/rfc8620/set.rs#L126)); `JmapChanges::new` likewise takes `method` and `capabilities` ([changes.rs L97](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/rfc8620/changes.rs#L97)). So sift can define its own `Email` struct with a `snoozed: Option<SnoozeDetails>` field, run `Email/get` through `JmapGet` with `urn:ietf:params:jmap:mail:snooze` in the capability list, and send a `snoozed` object through `JmapSet` or `send_raw`. The typed mail layer is less open: `JmapEmail` is a fixed struct without `snoozed` ([email.rs L31](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/rfc8621/email.rs#L31)) (unknown keys are ignored since no struct uses `deny_unknown_fields`), `JmapEmailProperty` is a closed enum ending at `Headers`, `JmapEmailGet` and `JmapEmailQuery` hardcode `using` to core and mail, and `JmapEmailPatch` only expresses keyword and mailbox patches ([email/set.rs](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/rfc8621/email/set.rs)). Snooze therefore means bypassing the `rfc8621::email` convenience types and using `rfc8620` generics for Email/get and Email/set, which is what those generics are for.

Thread and Email query, and changes: `JmapEmailQueryOptions` has `filter`, `sort`, `position`, `anchor`, `anchor_offset`, `limit`, `calculate_total`, `collapse_threads` and `properties`, and its output returns `emails`, `total`, `position` and `query_state`; the coroutine batches Email/query with Email/get through a result reference ([email/query.rs L248](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/rfc8621/email/query.rs#L248)). `collapse_threads` and anchors landed after 0.6.0, on 2026-10-10, and are unreleased at the time of writing. `JmapEmailChanges` returns `new_state`, `has_more_changes`, `created`, `updated`, `destroyed` ([rfc8620/changes.rs L76](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/rfc8620/changes.rs#L76)). `JmapThreadGet` and `JmapThreadChanges` exist with `JmapThread { id, email_ids }` ([thread.rs](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/rfc8621/thread.rs)).

Blob download: `JmapSession::resolve_download_url(account_id, blob_id, name, type)` fills the template with percent-encoded values ([session.rs L66](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/rfc8620/session.rs#L66)), and `JmapBlobDownload::new(auth, url)` writes an HTTP/1.1 GET with the `Host` taken from that URL ([blob_download.rs L94](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/rfc8620/blob_download.rs#L94)). The catch is at the client layer: `JmapClientStd` owns one boxed stream connected to the session host ([client.rs L296](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/client.rs#L296), [connect L364](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/client.rs#L364)), and `blob_download` writes the GET to that same stream ([L516](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/client.rs#L516)). With Fastmail the download host differs from `api.fastmail.com`, so sift would have to open a second TLS connection to `www.fastmailusercontent.com` itself (a second `JmapClientStd::connect` to that URL, or `set_stream`) and run the download coroutine on it. The coroutine design supports that; the std client does not do it for you.

Push: `JmapEventSource::new(session, auth, types, ping_seconds, close_after, shutdown)` builds the GET, expands template variables when present and appends query parameters when the URL is bare (fixed in 0.4.2 for the templated case), and yields one `JmapStateChange` per frame, with a shared `AtomicBool` for cooperative shutdown ([subscribe.rs L186](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/rfc8620/event_source/subscribe.rs#L186)). `JmapStateChange.changed` is `BTreeMap<String, JmapTypeStates>` keyed by plain strings, so unknown type names cannot break parsing ([event_source.rs L33](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/rfc8620/event_source.rs#L33)). The coroutine has its own yield type, so `JmapClientStd::run` cannot drive it; the client docs say it has "[its] own per-method loop" ([client.rs L311-317](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/client.rs#L311-L317)), and `connect` sets a five-second read timeout specifically "so the watch loop polls its shutdown atomic between SSE push frames" ([L403-406](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/client.rs#L403-L406)). Push needs its own connection and its own thread. No reconnect logic is included.

Async model: the crate is `#![no_std]` with I/O-free coroutines; "The caller owns the socket and pumps the coroutine with the bytes it read, whatever the runtime (blocking, async, in-memory tests)", and the shipped client is "a ready-made std-blocking pump" ([lib.rs](https://github.com/pimalaya/io-jmap/blob/919eab465ab620b323f9191ab8de2f640bc4a1d2/src/lib.rs)). The transport crate it uses, pimalaya-stream 0.3.0, is "deliberately std and blocking" and its docs say no async twin is planned ([docs.rs pimalaya-stream](https://docs.rs/pimalaya-stream/latest/pimalaya_stream/)). The Pimalaya architecture notes say "The library does not choose blocking vs async for you" but ship no async driver ([ARCHITECTURE.md](https://github.com/pimalaya/.github/blob/master/ARCHITECTURE.md)). For a tokio ratatui loop there are two options: run `JmapClientStd` on a dedicated thread (or `spawn_blocking`) and talk to it over channels, or write a tokio pump that feeds the coroutines from a `tokio_rustls` stream. The first is straightforward; the second is new code sift would own, including HTTP/1.1 over TLS with no HTTP/2 and no connection pooling, since io-http is HTTP/1.1 only.

## Hand-rolled reqwest plus serde

The pieces sift would use: reqwest 0.13.5 (MIT OR Apache-2.0), whose `Client` "is asynchronous (requiring Tokio)", with the `stream` feature for streaming bodies and `rustls` for TLS ([docs.rs reqwest](https://docs.rs/reqwest/latest/reqwest/)); serde and serde_json for the request and response objects; and for SSE either eventsource-stream 0.2.3 (MIT OR Apache-2.0, a parser that turns a byte stream into events, with only futures-core, nom and pin-project-lite as dependencies; [docs.rs](https://docs.rs/eventsource-stream/latest/eventsource_stream/)) or reqwest-eventsource 0.6.0, which adds retry but as of its docs depends on `reqwest ^0.12.0`, one major version behind ([docs.rs](https://docs.rs/reqwest-eventsource/latest/reqwest_eventsource/)).

What sift would write: a session fetch and `JmapSession` struct (capabilities as `BTreeMap<String, Value>`, URLs as strings); a `Request { using: Vec<String>, method_calls: Vec<(String, Value, String)> }` with a response that is `Vec<(String, Value, String)>` plus `sessionState`; typed argument and result structs for the handful of methods sift uses (Mailbox/get, Email/query with `collapseThreads`, Email/get, Email/set, Email/changes, Thread/get); a download function that fills the `downloadUrl` template and GETs with the bearer header; and an SSE loop over `bytes_stream()` with reconnect and `Last-Event-ID`. The RFC 8620 request and response objects are three fields each, and the Email object fields sift needs are the ones listed under RFC 8621 §4.1. Snooze is one more field on the Email struct and one more string in `using`. For scale, the io-jmap files covering the same ground (request, send, session and session fetch, get, set, query, changes, blob download, event source) total about 3,300 lines including their doc examples and unit tests; sift's version would be smaller because it would be typed for its own six methods rather than generic.

What sift would not get: result-reference helpers, typed per-object set errors, upload, and the live Fastmail and Stalwart integration tests that io-jmap runs on every push.

## Recommendation

Do not build on jmap-client. Snooze requires forking it in three places (the `URI` enum, the `Email` struct and its header catch-all, and the set builder), the probe shows an Email carrying `snoozed` fails to parse even as `null`, and two open 2026 issues report that it does not work against Fastmail without workarounds: the eleven-capability `using` list (#32) and the SSE parser rejecting Fastmail's opening comment (#36). Its async model is the best fit of the three for ratatui on tokio, but the fit does not outweigh needing a fork for the must-have feature.

Between io-jmap and hand-rolling, the deciding factor is the async model. io-jmap can do everything sift needs without a fork, is tested against Fastmail in CI, and keeps capabilities and method calls as plain strings and JSON, but its only shipped driver is blocking HTTP/1.1 on a single connection per host, its push loop is bespoke, downloads need a second connection, and sift would hold a worker thread plus channels between the TUI and JMAP, or write its own tokio pump. The crate is four months old with a breaking change in most releases, which means tracking it closely during the v1 build.

Recommendation: hand-roll a small JMAP module on reqwest 0.13 and serde, with eventsource-stream for push. Sift uses six JMAP methods, one download URL and one SSE stream; the request and response envelopes are three fields each; and every Fastmail-specific detail (the snooze capability, the `snoozed` property, the `snoozed` mailbox role, the separate download host, the bare `eventSourceUrl`) is then a line in sift's own code rather than a workaround around someone else's types. It keeps the whole app on one tokio runtime, which matters for keeping the ratatui loop responsive, and it leaves no dependency whose next breaking release has to be absorbed before v1 ships. Use io-jmap's `rfc8620` module as the reference for the envelope, result references and set-error shapes while writing it; if sift later wants calendars or contacts over JMAP, revisit io-jmap, whose typed layers already cover both.
