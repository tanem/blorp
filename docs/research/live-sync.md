# Change detection while running

Research for ticket 04 (`.scratch/triage-tui/issues/04-live-sync.md`). Written 2026-10-14. The question: how should sift, a stateless Rust TUI that fetches the Fastmail Inbox once per launch and holds it in memory, notice changes while it runs?

## Recommendation

Use JMAP push over EventSource (RFC 8620 section 7.3) as the wake-up signal in v1, and poll the `/changes` methods on a timer as the fallback. Both paths call the same reconcile routine, which asks the server for `Email/changes` and `Mailbox/changes` since the state strings sift holds and applies the `created`, `updated` and `destroyed` ids to the in-memory queue. Do not build on WebSocket (RFC 8887): Fastmail does not advertise it in the session object. Do not build on `Email/queryChanges` in v1: it is not needed when the whole Inbox is in memory, and the server may refuse to calculate it for filters sift might add later.

The rest of this file gives the evidence.

## What the RFCs define

RFC 8620 section 7 describes push as a minimal signal: "The general model for push is simple and sends minimal data over the push channel: just enough for the client to know whether it needs to resync. The format allows multiple changes to be coalesced into a single push update and the frequency of pushes to be rate limited by the server. It doesn't matter if some push events are dropped before they reach the client; the next time it gets/sets any records of a changed type, it will discover the data has changed and still sync all changes." Two mechanisms exist: an event source resource for clients that can hold a connection open, and PushSubscription, where the server POSTs to a URL the client registers ([RFC 8620 section 7](https://www.rfc-editor.org/rfc/rfc8620.html#section-7)).

The push payload is a StateChange object: `@type` is `"StateChange"` and `changed` maps an account id to a TypeState, "a map. The keys are the type name "Foo" (e.g., "Mailbox" or "Email"), and the value is the "state" property that would currently be returned by a call to "Foo/get". The client can compare the new state strings with its current values to see whether it has the current data for these types. If not, the changes can then be efficiently fetched in a single standard API request (using the /changes type methods)." The same section notes that a client with its own `/set` in flight "can wait until the call completes and then compare if the new state string after the /set is the same as was pushed in the StateChange object; if so, and the old state of the /set response matches the client's previous state, it does not need to waste a request asking for changes it already knows" ([RFC 8620 section 7.1](https://www.rfc-editor.org/rfc/rfc8620.html#section-7.1)).

The event source is "a long running HTTP request, where the server can push data to the client by appending data without ending the response." On each change the server "pushes an event called "state" to any connected clients, with the StateChange object as the data." The server "SHOULD also send a new event id that encodes the entire server state visible to the user immediately after sending a "state" event", and on reconnect a client sends `Last-Event-ID` so the server "can use to work out whether the client has missed some changes. If so, it SHOULD send these changes immediately on connection." The session object's `eventSourceUrl` is a level 1 URI Template that "MUST contain variables called "types", "closeafter", and "ping"". `types` is a comma-separated list of type names or `*`; `closeafter` is `state` (server ends the response after one state event) or `no`; `ping` is a positive integer of seconds, and "If non-zero, the server MUST send an event called "ping" whenever this time elapses since the previous event was sent." The server may clamp the ping interval but "MUST NOT have a minimum allowed value higher than 30 or a maximum allowed value less than 300", and the ping event's data is a JSON object with an `interval` property carrying the interval actually in use. The client makes "an authenticated GET request to the event-source URL" ([RFC 8620 section 7.3](https://www.rfc-editor.org/rfc/rfc8620.html#section-7.3)).

RFC 8621 makes push mandatory for mail servers: "Servers MUST support the JMAP push mechanisms, as specified in [RFC8620], Section 7". It also defines the `EmailDelivery` push type, whose state string "MUST change whenever a new Email is added to the store, but it SHOULD NOT change upon any other change to the Email objects, for example, if one is marked as read or deleted" ([RFC 8621 section 1.5](https://www.rfc-editor.org/rfc/rfc8621.html#section-1.5)).

RFC 8887 moves JMAP onto a WebSocket. A server that supports it "MUST add a property named "urn:ietf:params:jmap:websocket" to the capabilities object" with `url` (a wss URI) and `supportsPush`. Authentication happens once, "by presenting a user's credentials in the HTTP request [RFC7235] that initiates the WebSocket handshake", and the client "MUST include the value "jmap" in the list of protocols for the "Sec-WebSocket-Protocol" header field". Push over the socket is opt-in via a `WebSocketPushEnable` message with `dataTypes` and an optional `pushState`; notifications are StateChange objects extended with a `pushState` token so a reconnecting client can get everything it missed ([RFC 8887 sections 3, 4.1, 4.2, 4.3.5](https://www.rfc-editor.org/rfc/rfc8887.html)). Nothing in RFC 8887 mentions keepalive pings; a client would rely on WebSocket ping/pong frames.

The polling alternative uses `/changes`. The method takes `sinceState` and an optional `maxChanges` and returns `oldState`, `newState`, `hasMoreChanges`, `created`, `updated` and `destroyed`. On overlaps: "If a record has been created AND updated since the old state, the server SHOULD just return the id in the "created" list but MAY return it in the "updated" list as well. If a record has been updated AND destroyed since the old state, the server SHOULD just return the id in the "destroyed" list but MAY return it in the "updated" list as well. If a record has been created AND destroyed since the old state, the server SHOULD remove the id from the response entirely. However, it MAY include it in just the "destroyed" list or in both the "destroyed" and "created" lists." When there are more changes than `maxChanges`, "the server SHOULD generate an update to take the client to an intermediate state, from which the client can continue to call "Foo/changes" until it is fully up to date. If it is unable to calculate an intermediate state, it MUST return a "cannotCalculateChanges" error response instead." Intermediate states are ordered: the server "MUST NOT return a record as created after a response that deems it as updated or destroyed, and it MUST NOT return a record as destroyed before a response that deems it as created or updated." On `cannotCalculateChanges`, "The client MUST invalidate its Foo cache." Servers "SHOULD be able to calculate changes from any state string that was given to a client within the last 30 days" ([RFC 8620 section 5.2](https://www.rfc-editor.org/rfc/rfc8620.html#section-5.2)).

`Mailbox/changes` adds `updatedProperties`: "If only the "totalEmails", "unreadEmails", "totalThreads", and/or "unreadThreads" Mailbox properties have changed since the old state, this will be the list of properties that may have changed", usable as a back-reference into `Mailbox/get` ([RFC 8621 section 2.2](https://www.rfc-editor.org/rfc/rfc8621.html#section-2.2)). `Thread/changes` and `Email/changes` are standard `/changes` methods; for `Email/changes` the RFC recommends "newer changes be returned first" when paging ([RFC 8621 sections 3.2 and 4.3](https://www.rfc-editor.org/rfc/rfc8621.html#section-4.3)). `Email.threadId` is "immutable; server-set", and an Email "MUST belong to one or more Mailboxes at all times (until it is destroyed)" ([RFC 8621 section 4.1.1](https://www.rfc-editor.org/rfc/rfc8621.html#section-4.1.1)).

`/queryChanges` keeps a cached query result list in sync via `removed` and `added` (id plus index). Its errors are `tooManyChanges` and `cannotCalculateChanges`, and a server tells the client up front whether it can support it through the `canCalculateChanges` field of the `/query` response ([RFC 8620 section 5.6](https://www.rfc-editor.org/rfc/rfc8620.html#section-5.6)). `Email/queryChanges` takes the extra `collapseThreads` argument that was used with `Email/query` ([RFC 8621 section 4.5](https://www.rfc-editor.org/rfc/rfc8621.html#section-4.5)).

Rate limits in the core spec are advertised rather than fixed. The session's `urn:ietf:params:jmap:core` object carries `maxConcurrentRequests`, `maxCallsInRequest`, `maxObjectsInGet`, `maxObjectsInSet` and size limits ([RFC 8620 section 2](https://www.rfc-editor.org/rfc/rfc8620.html#section-2)). Exceeding one yields the request-level problem type `urn:ietf:params:jmap:error:limit` with a `limit` property naming the limit ([RFC 8620 section 3.6.1](https://www.rfc-editor.org/rfc/rfc8620.html#section-3.6.1)); a `rateLimit` SetError exists for `/set` creates ([RFC 8620 section 5.3](https://www.rfc-editor.org/rfc/rfc8620.html#section-5.3)); and "JMAP servers MUST implement sensible limits to mitigate against resource exhaustion attacks" ([RFC 8620 section 8.5](https://www.rfc-editor.org/rfc/rfc8620.html#section-8.5)).

## What Fastmail supports

### Session object

Fastmail's developer page gives the session resource as `https://api.fastmail.com/jmap/session` and says to send an API token as `Authorization: Bearer {value}` ([fastmail.com/dev](https://www.fastmail.com/dev/)). Two public dumps of real Fastmail session objects show `"eventSourceUrl": "https://api.fastmail.com/jmap/event/"` and `"apiUrl": "https://api.fastmail.com/jmap/api/"`, a core capability of `maxConcurrentRequests: 10`, `maxCallsInRequest: 50`, `maxObjectsInGet: 4096`, `maxObjectsInSet: 4096`, `maxSizeRequest: 10000000`, and no `urn:ietf:params:jmap:websocket` key. The first dump, from an API-token session, lists `urn:ietf:params:jmap:core`, `urn:ietf:params:jmap:mail`, `urn:ietf:params:jmap:submission`, `urn:ietf:params:jmap:contacts` and `https://www.fastmail.com/dev/maskedemail` ([c9dev/penguin-mail fastmail-session.json](https://github.com/c9dev/penguin-mail/blob/fd6094e3ca13e5055d963f43a79f1709a269edd0/jmap/tests/data/fastmail-session.json)). The second lists 19 capabilities including Fastmail-private ones such as `https://www.fastmail.com/dev/performance` and `https://www.fastmail.com/dev/compress`, and still has no websocket capability ([dwin/fastmask successful_auth_response.json](https://github.com/dwin/fastmask/blob/fdf32947734ff3d4359c17ff31e59655eab73955/pkg/fastmail/examples/successful_auth_response.json)). A 2026 issue on another client reports that for some accounts the session's `apiUrl` is region-scoped (`https://phl.api.fastmail.com/jmap/api/`) with `eventSourceUrl` scoped the same way, so sift must use the URLs from the session rather than hardcoding them ([huacnlee/omamail issue 37](https://github.com/huacnlee/omamail/issues/37)).

Note that the public dumps show `eventSourceUrl` as a bare URL without the `{types}`, `{closeafter}` and `{ping}` template variables the RFC requires. One client's notes record the templated form `https://api.fastmail.com/jmap/event/?types={types}&closeafter={closeafter}&ping={ping}` as what "a typical Fastmail / Stalwart session advertises" ([fclairamb/solidping spec note](https://github.com/fclairamb/solidping/blob/c7479ed359f003f2255740871c287a7465174c56/specs/done/2026/05/2026-05-02-11-jmap-eventsource-url-template.md)). Both forms are seen, so the URL builder must handle either: expand the template when the variables are present, otherwise append the three parameters as a query string. aerc's go-jmap does the latter unconditionally (see below); meli expands the template.

### EventSource for API-token sessions

The authoritative record is the thread on Fastmail's own samples repository, answered by Fastmail staff ([fastmail/JMAP-Samples issue 7](https://github.com/fastmail/JMAP-Samples/issues/7)). On 2021-03-09 rjbs (Fastmail) wrote: "Unfortunately, Fastmail's EventSource doesn't allow non-Fastmail clients to connect, yet." On 2021-04-08 neilj (Fastmail) wrote: "Unfortunately Fastmail hasn't implemented the PushSubscription part of the API yet either." On 2022-08-09 rjbs wrote: "as of today, you can create personal API tokens on beta.fastmail.com, which *will* work to get you an EventSource connection. PushSubscription support is on the road map, but the timeline isn't rock solid yet." On 2022-10-03 rjbs closed the issue: "This hit production a few weeks ago, and so I'm closing this issue. I'm hoping for PushSubscriptions in early 2023."

The same thread records two deviations from the RFC as of early 2023. On 2023-01-30 rockorager (author of go-jmap and the aerc JMAP backend) reported that the event data had a `"type": "connect"` key instead of `"@type": "StateChange"`, with `changed` listing `Email`, `EmailDelivery`, `Mailbox` and `Thread` states; rjbs replied "You have found a bug. We'll look into it, thanks." On 2023-02-01 rockorager added that "the `ping` and `closeAfterState` URL params don't seem to change the behavior in any way." A Fastmail-shaped event captured in meli's test suite shows the current form: the first event arrives immediately after a `: new event source connection` comment, is `event: state`, and its data carries both `"@type":"StateChange"` and a trailing `"type":"connect"`, with `changed` keyed by the account id and listing `Email`, `AddressBook`, `ContactCard`, `Thread`, `EmailDelivery`, `Mailbox` and `Identity` ([meli melib/src/jmap/eventsource.rs, test_eventsource, commit 1ada94c](https://git.meli-email.org/meli/meli/src/commit/1ada94c384bb6196ac163fded7af7c1177e120d4/melib/src/jmap/eventsource.rs)). So the `@type` bug was fixed and the extra `type` key remains; a parser must ignore unknown keys. The initial event means sift gets the server's current state strings for free on every connect. On `ping`, a Rust daemon notes from observation that "Fastmail can hand us back 300s when we ask for 60s", that is, the ping parameter is now honoured but clamped to the RFC's outer bound ([jmibanez/jma-mail src/daemon/eventsource.rs](https://github.com/jmibanez/jma-mail/blob/1d31cfeb225a526459df5e597b6cbe2b5f114f84/src/daemon/eventsource.rs)). I found no observation of whether Fastmail sends event ids or honours `Last-Event-ID`; sift should not depend on it, which costs nothing because every connect delivers the current states anyway.

Two unauthenticated probes on 2026-10-13 corroborate that the endpoint exists and takes bearer tokens. `GET https://api.fastmail.com/jmap/event/` (with and without the three query parameters) returns `401` with `WWW-Authenticate: Bearer resource_metadata="https://api.fastmail.com/.well-known/oauth-protected-resource/jmap/event"` and the body `No Authorization header`. That metadata document names the resource `https://api.fastmail.com/jmap/event`, lists `"bearer_methods_supported": ["header"]` and points to `https://www.fastmail.com/dev/` as documentation. The same metadata is served for `/jmap/session`. These probes were run from this machine with curl; they sent no credentials and no contact address.

### WebSocket

No source shows Fastmail advertising `urn:ietf:params:jmap:websocket`. Neither public session dump has the key, and the fuller of the two includes Fastmail's private capabilities, so it is not a scope artefact. In the issue 7 thread a user wrote on 2022-03-22 that "both the event source and the websocket methods of getting Push updates aren't available" to non-Fastmail clients, and Fastmail's later replies address only EventSource. An unauthenticated `GET https://api.fastmail.com/jmap/ws` on 2026-10-13 returned `302` to `https://www.fastmail.com/developer`, not a `401` or an upgrade failure, so there is no evidence of a WebSocket endpoint at the obvious path. Cyrus IMAP, which Fastmail says is "the battle-tested server that stores your email, contacts, and calendars at Fastmail" ([fastmail.com/company/open-source](https://www.fastmail.com/company/open-source/)), lists RFC 8887 as implemented and RFC 8620 as implemented "except for PushSubscription" ([cyrusimap.org JMAP page](https://www.cyrusimap.org/imap/download/installation/http/jmap.html)), but Fastmail's public API front end does not expose it. The Fastmail developer page does not mention push, EventSource or WebSocket at all ([fastmail.com/dev](https://www.fastmail.com/dev/)).

### PushSubscription

Not implemented by Fastmail as of the last staff statement (rjbs, 2022-10-03, "hoping for PushSubscriptions in early 2023") and absent from Cyrus. It would also need a public HTTPS URL for the server to POST to, which a TUI does not have. Not an option.

### Rate limits

Fastmail documents no numeric request limits for the JMAP API. The developer page's only rate-limit text is under Masked Email: "To prevent abuse, there are rate limits in place. A standard JMAP `rateLimit` SetError will be returned on create if these are exceeded" ([fastmail.com/dev](https://www.fastmail.com/dev/)). The help centre's Account limits article says "Our rate limits are designed to be generous for individual users, but not for bulk sending" and gives one concrete figure, "a per-user limit of 500 (successful) logins per 10 minutes across all services", with no mention of API, JMAP or request rates ([Account limits](https://www.fastmail.help/hc/en-us/articles/1500000277382-Account-limits)). The API tokens help article covers scopes and read-only tokens and nothing about limits ([API tokens](https://www.fastmail.help/hc/en-us/articles/5254602856719-API-tokens)). The only hard numbers are the advertised capability limits above: 10 concurrent requests, 50 method calls per request, 4096 objects per `/get`. A bearer token is not a login in the 500-per-10-minutes sense, but a client that reconnects to the event source in a tight loop could plausibly be throttled, so reconnects must back off.

### Thread/changes and Email/queryChanges on Fastmail's backend

Cyrus tests pin down behaviour that matters for reconciliation. `Thread/changes` reports a thread as `created` when its first email arrives, as `updated` when a later email joins it or some of its emails are destroyed while others remain, and as `destroyed` when its last email is destroyed; with `maxChanges => 1` it returns `hasMoreChanges: true` and pages ([cyrus-imapd cassandane thread_changes](https://github.com/cyrusimap/cyrus-imapd/blob/70b4609342666db707a4529a72890d7efa3e6ac1/cassandane/tiny-tests/JMAPEmail/thread_changes)). When several threads changed under one modification sequence and `maxChanges` is too small to return them together, Cyrus returns `cannotCalculateChanges` rather than a partial page ([thread_changes_maxchanges_too_small_duplicate_modseqs](https://github.com/cyrusimap/cyrus-imapd/blob/70b4609342666db707a4529a72890d7efa3e6ac1/cassandane/tiny-tests/JMAPEmail/thread_changes_maxchanges_too_small_duplicate_modseqs)). So a `cannotCalculateChanges` can be caused by sift's own `maxChanges` choice, not only by a stale state.

For `Email/query`, Cyrus reports `canCalculateChanges: true` for an unfiltered query, for `inMailbox` sorted by `receivedAt`, and for `inMailbox` with a mutable `someInThreadHaveKeyword` sort, but `false` for `inMailbox` combined with a keyword condition, for a negated `inMailbox`, and for `inMailboxOtherThan`; the file is headed "These assertions are implementation-specific" ([implementation_email_query](https://github.com/cyrusimap/cyrus-imapd/blob/70b4609342666db707a4529a72890d7efa3e6ac1/cassandane/tiny-tests/JMAPEmail/implementation_email_query)). A plain `inMailbox` query with `Email/queryChanges` round-trips with empty `added` and `removed` ([email_querychanges_mailbox_or](https://github.com/cyrusimap/cyrus-imapd/blob/70b4609342666db707a4529a72890d7efa3e6ac1/cassandane/tiny-tests/JMAPEmail/email_querychanges_mailbox_or)). The queue's own query (Inbox, newest first) is in the supported set, but any future filter such as "unread only" would not be, which is one reason to keep `queryChanges` out of v1.

## How aerc and meli do it

aerc (Go, [worker/jmap/push.go at 0a43480](https://git.sr.ht/~rjarry/aerc/tree/0a43480356a0d846917e505fed2e381289561b89/item/worker/jmap/push.go)) runs `monitorChanges` in a goroutine: it builds a go-jmap `push.EventSource` with `Ping` taken from the `server-ping` account option, calls `Listen()` in a loop, and on any error posts the error to the UI and sleeps five seconds before reconnecting. go-jmap's EventSource ([core/push/eventsource.go at 25f7b38](https://github.com/rockorager/go-jmap/blob/25f7b38d24c6b330aea1c92cee2dea2d78fff1d2/core/push/eventsource.go)) appends `types`, `ping` and `closeafter` as query parameters to `Session.EventSourceURL`, requires a 200, scans the body line by line and decodes only `data` lines that follow `event: state` into a StateChange; it ignores `id` lines, never sends `Last-Event-ID`, and ignores `retry`. aerc's `handleChange` compares each pushed state with the cached `Mailbox`, `Email` and `Thread` states and builds one request containing `Mailbox/changes` with `Mailbox/get` back-references for `/created` and `/updated`, an `Email/queryChanges` per open folder with that folder's filter and `sinceQueryState`, `Email/changes` with `Email/get` back-references for `/updated` and `/created`, and `Thread/changes` with `Thread/get` back-references. It applies `destroyed` by deleting from its cache and posting removals, `created` and `updated` by storing the fetched objects and diffing `mailboxIds` against the cached copy to post per-folder removals and additions, and on a `MethodError` from `Email/queryChanges` it flushes that folder's cached contents. It never reads `hasMoreChanges` and has no `cannotCalculateChanges` handling beyond that flush (grep of `worker/jmap` finds neither identifier). Its manual says `server-ping` is "Interval the server should ping the client at when monitoring for email changes. The server may choose to ignore this value. By default, no ping will be requested from the server" ([doc/aerc-jmap.5.scd](https://git.sr.ht/~rjarry/aerc/tree/0a43480356a0d846917e505fed2e381289561b89/item/doc/aerc-jmap.5.scd)).

meli (Rust, melib 0.8.13 at commit 1ada94c) has a complete server-sent-events parser in [melib/src/jmap/eventsource.rs](https://git.meli-email.org/meli/meli/src/commit/1ada94c384bb6196ac163fded7af7c1177e120d4/melib/src/jmap/eventsource.rs): it expands the `eventSourceUrl` template with `types=*`, `closeafter=no`, `ping=300`, sends `Accept: text/event-stream` and `Cache-Control: no-cache`, authenticates with `Authorization: Bearer` when `use_token` is set (otherwise Basic), sends `Last-Event-ID` on reconnect when it saw an `id`, honours the stream's `retry` field by sleeping before reconnecting, and rejects any response that is not 2xx with `Content-Type: text/event-stream`. The backend's `watch` ([melib/src/jmap/mod.rs](https://git.meli-email.org/meli/meli/src/commit/1ada94c384bb6196ac163fded7af7c1177e120d4/melib/src/jmap/mod.rs)) takes only `state` events whose `@type` is `StateChange`, and for each account compares the pushed `Mailbox` and `Email` states with its cached ones, calling `mailbox_changed` or `email_changed` when they differ; `Thread` is not handled and `Identity` is a TODO. `email_changed` ([melib/src/jmap/connection.rs](https://git.meli-email.org/meli/meli/src/commit/1ada94c384bb6196ac163fded7af7c1177e120d4/melib/src/jmap/connection.rs)) loops: one request with `Email/changes` plus `Email/get` back-references for `/created` and `/updated`; it removes `destroyed` ids from the store, adds `created` envelopes to each of their mailboxes and updates counters, applies new flags for `updated` envelopes, then if `has_more_changes` sets `cached_state = new_state` and repeats, otherwise stores `new_state` and stops. `mailbox_changed` pages the same way. meli's `refresh` command runs `email_changed(None)` against the cached state, which is exactly the polling path.

Neither client handles `cannotCalculateChanges` by refetching. Neither uses WebSocket; go-jmap's README lists RFC 8887 as "Not started" ([rockorager/go-jmap README](https://github.com/rockorager/go-jmap)).

## Reconciling an in-memory queue

sift's queue is the set of threads with at least one email in the Inbox mailbox, ordered by date. At launch it fetches `Mailbox/get` (to learn the Inbox id and role mailboxes), `Email/query` with `inMailbox: <inbox>` sorted by `receivedAt`, then `Email/get` and `Thread/get` for the results. The `state` values returned by `Email/get`, `Thread/get` and `Mailbox/get` are the `sinceState` inputs for `/changes`; the `queryState` from `Email/query` is only for `queryChanges` and is not needed. The in-memory model should hold, per email: id, threadId, mailboxIds, keywords, receivedAt and the display fields; and per thread: the ordered email ids. A map from email id to thread id is essential because a `destroyed` id arrives with no other data.

The reconcile routine, run on every wake-up from either push or the timer, is:

1. Send one request: `Email/changes {sinceState: emailState, maxChanges: 500}`; `Email/get` with a back-reference to `/created` and the display properties; `Email/get` with a back-reference to `/updated` requesting at least `threadId`, `mailboxIds`, `keywords`, `receivedAt`; `Mailbox/changes {sinceState: mailboxState}`; `Mailbox/get` with back-references to `/updated` ids and `/updatedProperties`. `Thread/changes` is not required for queue membership because `Email/changes` is account-wide and `threadId` is immutable, so every email that joins or leaves a thread shows up as a created, updated or destroyed email; include it only if sift wants `Thread/get` to refresh email ordering inside a thread, and in that case it fits in the same request.
2. Apply `destroyed` first: remove each id from its thread via the id-to-thread map; a thread with no remaining Inbox emails leaves the queue. Then apply `created` and `updated` identically as upserts from the fetched objects: an email whose `mailboxIds` contains the Inbox adds or refreshes its thread in the queue, and one that no longer does is removed from the thread's Inbox set. Because an id may legally appear in more than one list, upsert and remove must be idempotent, and `Email/get` may return a `destroyed` id under `notFound`, which is ignored. The ordering guarantee for intermediate states means each page can be applied as it arrives.
3. If `hasMoreChanges` is true, set `sinceState = newState` and repeat from step 1, with a bound (say 20 pages) after which the routine falls through to a full refetch. Otherwise store `newState` as the new baseline.
4. On `cannotCalculateChanges` from any `/changes` call, retry once with `maxChanges` omitted (the Cyrus test shows an over-small `maxChanges` alone can cause the error). If it recurs, discard the in-memory model and run the launch fetch again; for a stateless client this is the whole cost and it is the same code path as startup. The RFC requires the cache to be invalidated in this case, and both aerc and meli skip this step.
5. Keep the user's position: identify the selected thread by id before applying changes and reselect it afterwards, falling back to the nearest neighbour if it left the queue.

The server-wins rule for races with sift's own actions is enough for v1: after a local `Email/set`, store the `newState` from the set response, so the next reconcile is a no-op if nothing else changed; when a push arrives mid-action, running reconcile after the set completes is idempotent. Undo keeps its own record of the previous state and is unaffected.

## Push versus polling for sift

EventSource costs one idle HTTPS connection and delivers changes within seconds; the pushed state strings let sift skip the `/changes` request entirely when nothing it cares about changed, and the first event on connect doubles as a baseline check. Its risks on Fastmail are the undocumented status of the endpoint (nothing on fastmail.com/dev, support confirmed only in a GitHub issue), the extra `type` key, the past bug with `ping`, the unknown `Last-Event-ID` behaviour, and connections dropped by proxies or sleep. Polling `/changes` has none of those risks and costs one small request per interval even when idle; the RFC's 30-day window for state strings makes a 60-second interval safe for an interactive session, and the advertised `maxConcurrentRequests` of 10 is far above what a single-user TUI issues. Because the pushed payload carries no record data, both paths converge on the same reconcile routine, so supporting both is cheap.

The v1 plan is therefore: open the event source with `types=Email,Mailbox` (add `Thread` if `Thread/changes` is used), `closeafter=no`, `ping=300`; accept any 2xx `text/event-stream` response; ignore comments and unknown keys; treat each `state` event as "run reconcile if the pushed state differs from ours"; and watch for pings, treating silence longer than the server's reported `interval` plus slack as a dead connection. Reconnect with exponential backoff from a few seconds to a minute. While the event source is down for any reason, including a non-2xx response, a wrong content type or repeated parse errors, run reconcile on a 60-second timer, and keep a manual refresh key that runs it on demand. Both paths are the same function, so the fallback is always exercised. Before building, confirm against the live account with the API token that the session's `eventSourceUrl` is as expected and that a `curl -N -H "Authorization: Bearer ..." "<eventSourceUrl>?types=Email,Mailbox&closeafter=no&ping=30"` yields the initial `state` event and then `ping` events with their `interval`.
