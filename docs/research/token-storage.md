# Token storage and secret handling

Research for ticket 03 of the triage-TUI map. Question: how sift (a Rust ratatui TUI on macOS, single user, public open-source repository) should store and handle a Fastmail JMAP API token. Sources were read on 2026-10-14; crate versions and URLs are as of that date. Quotations are verbatim from the cited source.

## 1. What a Fastmail API token is

Fastmail's developer page says API tokens are for "testing purposes, or building an app for just yourself", and that distributed apps should use OAuth instead ([fastmail.com/dev](https://www.fastmail.com/dev/)). A token is sent as a bearer credential: "To use an API token, add an `Authorization` header set to `Bearer {value}`" ([fastmail.com/dev](https://www.fastmail.com/dev/)). The session resource is `https://api.fastmail.com/jmap/session` ([fastmail.com/dev](https://www.fastmail.com/dev/)). Bearer credentials follow RFC 6750: "Clients SHOULD make authenticated requests with a bearer token using the "Authorization" request header field" ([RFC 6750 §2.1](https://www.rfc-editor.org/rfc/rfc6750.html#section-2.1)).

Tokens are created under Settings, Privacy & Security, "Connected apps & API tokens". The token is shown once: the help article says to copy it somewhere safe before clicking Done "because you can't view it again" ([Fastmail help: API tokens](https://www.fastmail.help/hc/en-us/articles/5254602856719-API-tokens)). The article does not mention an expiry. Fastmail's own advice: "Treat your API token like an app password", select only the access the integration needs, do not share it, and remove tokens for apps no longer used or trusted, or if a device is lost ([Fastmail help: API tokens](https://www.fastmail.help/hc/en-us/articles/5254602856719-API-tokens)).

Revocation is manual: open the token in Manage API tokens, click Remove access, confirm. The article warns "this action cannot be undone". The same screen shows what a token can access, when access was first granted, and when it was most recently used ([Fastmail help: API tokens](https://www.fastmail.help/hc/en-us/articles/5254602856719-API-tokens)).

Bearer tokens must be protected by the client: "Client implementations MUST ensure that bearer tokens are not leaked to unintended parties", must be sent over TLS, and "The client MUST validate the TLS certificate chain when making requests to protected resources" ([RFC 6750 §5.3](https://www.rfc-editor.org/rfc/rfc6750.html#section-5.3)). JMAP itself requires TLS 1.2 or later and certificate chain validation ([RFC 8620 §8.1](https://www.rfc-editor.org/rfc/rfc8620.html#section-8.1)), and recommends per-client credentials so that "access [can] be individually revoked" ([RFC 8620 §8.2](https://www.rfc-editor.org/rfc/rfc8620.html#section-8.2)). RFC 8620 §2 says "How to obtain credentials is out of scope for this document" ([RFC 8620 §2](https://www.rfc-editor.org/rfc/rfc8620.html#section-2)).

## 2. Minimal scopes for the v1 action set

The JMAP token scopes Fastmail offers are: "Read-only access" (view and download only), "Email" ("Download, modify, and permanently delete mail"), "Email submission" ("Send mail. This requires Email to also be selected"), "Contacts and contact groups", and "Masked Email" ([Fastmail help: API tokens](https://www.fastmail.help/hc/en-us/articles/5254602856719-API-tokens)). The OAuth scope URNs on the developer page (`urn:ietf:params:jmap:mail`, `urn:ietf:params:jmap:submission`, and so on) apply to OAuth clients, not API tokens ([fastmail.com/dev](https://www.fastmail.com/dev/)).

Every v1 action is an `Email/set` call within the mail capability. RFC 8621 §4.6 says `Email/set` "encompasses" "Changing the keywords of an Email (e.g., unread/flagged status)", changing mailboxes, and "Deleting Emails", and that clients can "add/remove individual ones using the JMAP patch syntax" ([RFC 8621 §4.6](https://www.rfc-editor.org/rfc/rfc8621.html#section-4.6)). Read state and flag are the `$seen` and `$flagged` keywords ([RFC 8621 §4.1.1](https://www.rfc-editor.org/rfc/rfc8621.html#section-4.1.1)). Archive, move, and spam are `mailboxIds` patches (spam being a move into the mailbox whose role is junk). Delete is a move to the trash role: "To just delete an Email to trash, simply change the "mailboxIds" property" so the Email is in "the Mailbox with a "role" property equal to "trash"" ([RFC 8621 §4.6](https://www.rfc-editor.org/rfc/rfc8621.html#section-4.6)). Snooze (ticket 01) is also an `Email/set` property change if Fastmail implements the expired draft; whether a separate capability gate exists is for ticket 01 to confirm.

So the token needs exactly the Email scope. Read-only is insufficient because every action mutates; Email submission is not needed because v1 has no compose, reply, or forward; Contacts and Masked Email are irrelevant. fastmail-cli reports when a token lacks a capability with the message "Your API token may be read-only" after checking the session's `capabilities` map ([fastmail-cli src/jmap/mod.rs](https://github.com/radiosilence/fastmail-cli/blob/main/src/jmap/mod.rs)); sift should do the same check at startup so a wrongly scoped token fails early with a clear message.

## 3. Storing the token on macOS

### 3.1 Keychain mechanics

macOS has two keychain implementations: "File-based keychain" and "Data protection keychain". "The SecItem API can target either implementation. It defaults to targeting the file-based keychain." Apple recommends defaulting to the data protection keychain, but "The data protection keychain is only available to programs running in a user context, like an app or an app extension" and its access model is "keychain access groups", which depend on code signing and entitlements ([Apple TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)). "The file-based keychain uses access control lists (SecAccess)" ([Apple TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)).

File-based keychain items are protected by an ACL whose entries "each contain an array of operations and an array of apps trusted to carry out those operations with the item". If the calling app is trusted, access is granted; "Otherwise, the system prompts the user for confirmation. The user may choose to Deny, Allow, or Always Allow the access", and Always Allow "adds the app to the list of trusted apps for that entry" ([Apple: Access Control Lists](https://developer.apple.com/documentation/security/access-control-lists)). The `security(1)` man page says: "By default, the application which creates an item is trusted to access its data without warning", and the partition list is "an extra parameter in the ACL which limits access to the item based on an application's code signature" ([security(1)](https://keith.github.io/xcode-man-pages/security.1.html)).

Consequence for a locally built Rust binary: trust is keyed to the code signature. Apple DTS (Quinn) on recurring prompts after rebuilds: "the vast majority of folks hit this problem because their executable is not signed in a stable fashion, that is, it's unsigned (not an option an Apple silicon) or ad hoc signed" ([Apple Developer Forums thread 125794](https://developer.apple.com/forums/thread/125794)). A `cargo build` binary is ad hoc signed, so each rebuild is a different app to the keychain and the first keychain read after a rebuild prompts. This is expected behaviour, not a bug in sift; the developer clicks Allow or Always Allow, or signs dev builds with a stable self-signed identity to stop the prompts. The prompt is also a security property: another process cannot silently read the item.

### 3.2 The keyring crate ecosystem

The `keyring` crate was restructured at version 4. keyring 4.2.0's documentation says applications "should instead be linking to the keyring-core library and any specific credential stores they want to use" ([docs.rs keyring 4.2.0](https://docs.rs/keyring/latest/keyring/)); its README says the same, that developers should "take dependencies on the keyring-core crate and the specific credential stores they want to use" ([keyring-rs README](https://github.com/open-source-cooperative/keyring-rs/blob/master/README.md)). The default `v1` feature of keyring 4 still gives the old all-in-one API, enabling `apple-native-keyring-store/keychain` on macOS ([docs.rs keyring features](https://docs.rs/crate/keyring/latest/features)). keyring 3.6.3 (the previous line) has no default features and an `apple-native` feature that "Provides access to the Keychain credential store on macOS and iOS" ([docs.rs keyring 3.6.3](https://docs.rs/keyring/3.6.3/keyring/)).

keyring-core 1.0.1 provides `Entry::new(service, user)`, `set_password(&str)`, `get_password() -> String`, `set_secret(&[u8])`, `get_secret() -> Vec<u8>`, and `delete_credential()` ([docs.rs keyring-core Entry](https://docs.rs/keyring-core/latest/keyring_core/struct.Entry.html)). Its error enum includes `NoEntry` ("no underlying credential entry in the platform for this entry"), `NoStorageAccess` (the store "could not be accessed", for example a locked store), `PlatformFailure`, `Ambiguous`, and `NoDefaultStore` ([docs.rs keyring-core Error](https://docs.rs/keyring-core/latest/keyring_core/error/enum.Error.html)).

apple-native-keyring-store 1.0.2 has two modules. Its README: "If you are writing client apps that are _not_ code-signed by a provisioning profile (e.g., command-line apps), then you should use the `keychain` module of this store, which accesses the macOS keychain"; the `protected` module (data protection keychain) needs a provisioning profile, and in an unsigned app it fails with "`PlatformError` with code `-34018` *A required entitlement isn't present.*" ([apple-native-keyring-store README](https://github.com/open-source-cooperative/apple-native-keyring-store/blob/main/README.md)). The `keychain` module creates "a generic credential in the store's keychain whose _account_ attribute holds the user and whose _service_ attribute holds the service"; "By default, the 'User' (aka login) keychain is used"; generic credentials are unique per keychain by account and service, "so there is no chance of ambiguity"; neither may be the empty string ([docs.rs apple-native-keyring-store keychain](https://docs.rs/apple-native-keyring-store/latest/apple_native_keyring_store/keychain/index.html)). Its `Cargo.toml` shows `keychain = ["security-framework"]` and `security-framework` version 3.7, and `src/keychain.rs` calls `SecKeychain::set_generic_password`, `find_generic_password`, and `SecKeychain::default_for_domain` from the `security-framework` crate ([apple-native-keyring-store src/keychain.rs](https://github.com/open-source-cooperative/apple-native-keyring-store/blob/main/src/keychain.rs)).

### 3.3 Direct security-framework use

security-framework 3.7.0's `passwords` module exposes `set_generic_password(service: &str, account: &str, password: &[u8]) -> Result<()>` ("Creates or updates a keychain entry"), `generic_password(options) -> Result<Vec<u8>>` (fails with `errSecItemNotFound` if absent), and `delete_generic_password` ([docs.rs security-framework passwords](https://docs.rs/security-framework/latest/security_framework/passwords/index.html), [set_generic_password](https://docs.rs/security-framework/latest/security_framework/passwords/fn.set_generic_password.html), [generic_password](https://docs.rs/security-framework/latest/security_framework/passwords/fn.generic_password.html)). The `os::macos::keychain::SecKeychain` type has `default()`, `default_for_domain(SecPreferencesDomain)`, `set_generic_password(&self, service, account, password: &[u8])`, and `find_generic_password(&self, service, account) -> Result<(SecKeychainItemPassword, SecKeychainItem)>` ([docs.rs SecKeychain](https://docs.rs/security-framework/latest/security_framework/os/macos/keychain/struct.SecKeychain.html)).

### 3.4 Comparison and recommendation

Both routes end in the same `SecItem` generic-password item in the login keychain with the same ACL behaviour, because the keyring store is a thin wrapper over security-framework (section 3.2). The differences are: (a) keyring-core adds a platform-neutral error model (`NoEntry`, `NoStorageAccess`, and so on) and an `Entry` abstraction, and makes a later Linux port a feature flag; (b) direct security-framework is one dependency fewer (apple-native-keyring-store pulls `keyring-core` and `log`) and gives access to `PasswordOptions`/`AccessControlOptions` if sift ever wants to tune the ACL; (c) keyring-core's `get_password` returns an owned `String` that sift must immediately move into a `SecretString` (section 6).

Recommendation: use `keyring-core` plus `apple-native-keyring-store` with only the `keychain` feature. The item is `service = "sift"`, `account = <Fastmail username or the string "fastmail">`. Do not use the `protected` module; sift is not provisioned. Do not use keyring 4's `v1`/`cli` features (they enable stores sift does not need). Direct security-framework is acceptable if the maintainers prefer fewer crates; the standard below is written so either implementation satisfies it.

## 4. Environment-variable override

Why an override: CI and scripted dry runs cannot answer a keychain prompt, and keychain prompts are per code signature (section 3.1). The pattern is common: fastmail-cli reads `FASTMAIL_API_TOKEN` first and falls back to the config file ("Env vars take precedence") ([fastmail-cli README](https://github.com/radiosilence/fastmail-cli/blob/main/README.md), [src/config.rs](https://github.com/radiosilence/fastmail-cli/blob/main/src/config.rs) `get_token`). GitHub Actions passes secrets to steps through the `secrets` context "as an environment variable" and masks registered secret values in logs; the docs still say "Be careful that your secrets do not get printed when your workflow runs" and "Avoid passing secrets between processes from the command line, whenever possible" ([GitHub: Using secrets in GitHub Actions](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions)).

Exposure of environment variables: on macOS `ps -E` will "Display the environment as well" for a process ([ps(1)](https://keith.github.io/xcode-man-pages/ps.1.html)); on Linux `/proc/pid/environ` holds the initial environment and "Permission to access this file is governed by a ptrace access mode PTRACE_MODE_READ_FSCREDS check" ([proc_pid_environ(5)](https://man7.org/linux/man-pages/man5/proc_pid_environ.5.html)), so same-user processes can read it. Command-line arguments are worse (visible in `ps` output to everyone and in shell history), which is why fastmail-cli reads the token from stdin during setup: "the token is read from stdin so it stays out of shell history, `ps`, and the process environment" ([fastmail-cli README](https://github.com/radiosilence/fastmail-cli/blob/main/README.md)). Conclusion: the env var is for non-interactive contexts only, never the primary store, and the token is never accepted as a command-line argument.

clap's `env` feature supports `Arg::env` (value read from the variable when the argument is absent; command-line value overrides it) and `Arg::hide_env_values`, which hides env values in `--help`, "useful when environment variables contain sensitive values" ([docs.rs clap Arg](https://docs.rs/clap/latest/clap/struct.Arg.html)). If sift declares the override through clap it must set `hide_env_values(true)`; the simpler route is `std::env::var` read once at startup ([std::env::var](https://doc.rust-lang.org/std/env/fn.var.html)) and moved into a `SecretString`.

## 5. How other clients handle tokens

aerc (Go, master at 2026-10-14): the JMAP account's `source` URL may embed the password (`jmap+oauthbearer://:s3cr3t@example.com/jmap/session`), or `source-cred-cmd` names a command "run using _sh -c command_" whose stdout is the password; "If a password is specified in the *source* option, the password will take precedence over this command"; "Your source credentials must have the _urn:ietf:params:jmap:mail_ capability" ([aerc doc/aerc-jmap.5.scd](https://git.sr.ht/~rjarry/aerc/tree/master/item/doc/aerc-jmap.5.scd)). In code, `RemoteConfig.ConnectionString` runs `exec.Command("sh", "-c", c.PasswordCmd)`, trims stdout, and splices it into the URL with `url.UserPassword`; the result is cached in memory only if `outgoing-cred-cmd-cache` is true ([aerc config/accounts.go](https://git.sr.ht/~rjarry/aerc/tree/master/item/config/accounts.go)). The JMAP worker then calls `w.client.WithAccessToken(pass)` for `+oauthbearer` and `WithBasicAuth` otherwise ([aerc worker/jmap/connect.go](https://git.sr.ht/~rjarry/aerc/tree/master/item/worker/jmap/connect.go)). Lesson: aerc delegates storage to an external secret manager via a command and never writes the token itself; the token in the config file is allowed but documented as the lesser option. aerc has no OS keychain integration of its own.

himalaya (Rust CLI, 2.2.1): "Every `*.passwd` / `*.password` / `*.token` field accepts either a raw literal or a shell command that prints the secret on stdout. The raw form is convenient for testing but should not be used in production" and "Native keyring support was removed in v2. Use a third-party keyring CLI (`pass`, `secret-tool`, `gopass`…) as the `command`" ([himalaya README](https://github.com/pimalaya/himalaya/blob/master/README.md)). The v1 line had `{ keyring = <secret-entry> }` from 0.8.0 ("Added keyring support, which means Himalaya can now use your system's global keyring") ([himalaya CHANGELOG](https://github.com/pimalaya/himalaya/blob/master/CHANGELOG.md)). JMAP auth is `jmap.auth.bearer.token.{raw,command}` or `jmap.auth.header.{raw,command}` ([himalaya config.sample.toml](https://github.com/pimalaya/himalaya/blob/master/config.sample.toml)). In code the resolved credential is a `secrecy::SecretString` and the header is built as `format!("Bearer {}", token.expose_secret()).into()` ([himalaya src/jmap/client.rs](https://github.com/pimalaya/himalaya/blob/master/src/jmap/client.rs)); `secrecy = "0.10"` is in `Cargo.toml`. A recent changelog entry records a fix where the IMAP library's `LOGIN` and `AUTHENTICATE` "no longer log credentials at trace level" ([himalaya CHANGELOG, Unreleased](https://github.com/pimalaya/himalaya/blob/master/CHANGELOG.md)), which is the leak class the rules below prevent. Lessons: wrap the token in `SecretString` from the moment it is resolved; treat raw tokens in config as a test-only path; the maintainer chose to drop an in-process keyring dependency and shell out instead.

radiosilence/fastmail-cli (Rust, 3.6.0): the token is pasted at a prompt or piped on stdin; it is stored in `~/.config/fastmail-cli/config.toml` "with `0600` permissions (directory `0700`)", "written atomically via rename, and the path is refused if it's a symlink" ([fastmail-cli README](https://github.com/radiosilence/fastmail-cli/blob/main/README.md)). `src/config.rs` confirms: `create_private_dir` uses `.mode(0o700)` then `set_permissions(0o700)`; `write_private_file` uses `.create_new(true).mode(0o600)`; `save` checks `symlink_metadata(...).file_type().is_symlink()`, writes `config.toml.tmp`, then `fs::rename`. `FASTMAIL_API_TOKEN` takes precedence over the file ([fastmail-cli src/config.rs](https://github.com/radiosilence/fastmail-cli/blob/main/src/config.rs)). Weaknesses to avoid: `Config` and `CoreConfig` derive `Debug` with the token as a plain `Option<String>`, so `{:?}` would print it; the JMAP client holds `token: String` and does not use `secrecy` or `zeroize` (neither is in `Cargo.toml`) ([fastmail-cli Cargo.toml](https://github.com/radiosilence/fastmail-cli/blob/main/Cargo.toml)). It does map HTTP 401 to a typed `Error::InvalidToken` on the session fetch and every API call, and treats it as fatal in its watch loop rather than retrying ([fastmail-cli src/jmap/mod.rs](https://github.com/radiosilence/fastmail-cli/blob/main/src/jmap/mod.rs), [src/jmap/watch.rs](https://github.com/radiosilence/fastmail-cli/blob/main/src/jmap/watch.rs)). It has no keychain support.

None of the three stores the token in the macOS keychain in-process. sift's decision (map: "API token stored in the macOS keychain") is stricter than all three and is supported by the keyring ecosystem described in section 3.

## 6. In-process handling: never log, echo, or serialise

secrecy 0.10.3 provides `SecretBox<S>` with `pub type SecretString = SecretBox<str>` and `impl From<String> for SecretString`. Its stated goals: "Make secret access explicit and easy-to-audit via the `ExposeSecret` and `ExposeSecretMut` traits", "Prevent accidental leakage of secrets via channels like debug logging", and "Ensure secrets are wiped from memory on drop securely (using the `zeroize` crate)" ([docs.rs secrecy](https://docs.rs/secrecy/latest/secrecy/)). Its `Debug` impl writes `SecretBox<{type}>([REDACTED])`; there is no `Display` impl; `Drop` calls `zeroize`; `Clone` exists only for `CloneableSecret` types, which do not include `str`; `Serialize` exists only for types implementing the `SerializableSecret` marker, "done deliberately to prevent accidental exfiltration of secrets via `serde` serialization", while `Deserialize` is available behind the `serde` feature ([secrecy src/lib.rs](https://github.com/iqlusioninc/crates/blob/main/secrecy/src/lib.rs), [docs.rs SecretBox](https://docs.rs/secrecy/latest/secrecy/struct.SecretBox.html)). The only way to read the value is `expose_secret()`, "the only method providing access to a secret" ([secrecy src/lib.rs](https://github.com/iqlusioninc/crates/blob/main/secrecy/src/lib.rs)).

zeroize's limits: it guarantees the zeroing "can't be "optimized away" by the compiler", but for `Vec`, `String`, and `CString` it "cannot guarantee copies of the data were not previously made by buffer reallocation", registers cannot be cleared, and microarchitectural attacks remain possible ([docs.rs zeroize 1.9.1](https://docs.rs/zeroize/latest/zeroize/)). So the token should be moved into `SecretString` once and never copied into intermediate `String`s or `format!` results that outlive the request. himalaya's `format!("Bearer {}", ...).into()` creates one transient `String` that is immediately boxed; that is acceptable.

HTTP layer: `http` 1.5.0's `HeaderValue::set_sensitive(true)` marks a value as sensitive; `is_sensitive` docs say the `Debug` implementation masks sensitive values and caches and HPACK encoders can skip them ([docs.rs http HeaderValue](https://docs.rs/http/latest/http/header/struct.HeaderValue.html)); the `Debug` impl writes the literal `Sensitive` ([http src/header/value.rs](https://github.com/hyperium/http/blob/master/src/header/value.rs)). reqwest 0.13's `RequestBuilder::bearer_auth` builds `format!("Bearer {token}")` and passes it through `header_sensitive(AUTHORIZATION, value, true)`, which calls `set_sensitive(true)`; `Request`'s `Debug` prints headers, so with `bearer_auth` the Authorization line shows `Sensitive` ([reqwest src/async_impl/request.rs](https://github.com/seanmonstar/reqwest/blob/master/src/async_impl/request.rs)). If sift builds the header itself (for example with a different HTTP crate), it must call `set_sensitive(true)` or the equivalent. Request and response logging at debug/trace level must never dump raw request bytes.

Logging: tracing records fields with `Debug` (`?`) or `Display` (`%`) and `#[instrument]` records function arguments "using `fmt::Debug`" ([docs.rs tracing 0.1.44](https://docs.rs/tracing/latest/tracing/)). With `SecretString` the `Debug` output is redacted, but a `&str` from `expose_secret()` passed into a span is not. The rule is that `expose_secret()` is called only at the single point where the header is built, and functions that receive the token take `&SecretString`, so `#[instrument]` is safe. Skip the client struct in `#[instrument(skip(self))]` regardless.

Panics: the default panic hook "prints a message to standard error and generates a backtrace if requested" ([std::panic::set_hook](https://doc.rust-lang.org/std/panic/fn.set_hook.html)). A panic message cannot contain the token unless code formats it into one, which the `SecretString` rules prevent; `unwrap()` on a `Result<_, E>` prints `E`'s `Debug`, so error types must not carry the token either. The TUI needs a panic hook anyway to restore the terminal; that hook must not print any struct that could hold a secret.

Error messages: keyring and HTTP errors should be mapped to sift's own error type at the boundary. Never include the token, the Authorization header, or the raw session JSON in an error. The 401 handling in section 8 returns a fixed string.

Dry run: CONTEXT.md defines dry run as "A mode in which actions are logged instead of sent to Fastmail". The dry-run log records thread ids and the action, never request headers.

## 7. Config file and permissions

The token is not in the config file. The config file holds the Fastmail username, keybindings, and preferences, so it has no secret and does not need special permissions; the keychain holds the token. If a `--token-file` style option is ever added it must follow the fastmail-cli pattern: create with `OpenOptions::mode(0o600)` and `create_new(true)` (the OS "masks out bits with the system's `umask`" so 0o600 is a ceiling, which is fine) ([std OpenOptionsExt::mode](https://doc.rust-lang.org/std/os/unix/fs/trait.OpenOptionsExt.html)), directory 0o700, write to a temp file then `rename`, refuse symlinks ([fastmail-cli src/config.rs](https://github.com/radiosilence/fastmail-cli/blob/main/src/config.rs)).

Config location: the `directories` crate (6.0.0) puts `ProjectDirs::config_dir` at `$HOME/Library/Application Support/<project>` on macOS and `$XDG_CONFIG_HOME/<project>` or `$HOME/.config/<project>` on Linux ([docs.rs directories ProjectDirs](https://docs.rs/directories/latest/directories/struct.ProjectDirs.html)); XDG defines `$XDG_CONFIG_HOME` with default `$HOME/.config` ([XDG Base Directory Specification](https://specifications.freedesktop.org/basedir/latest/)). fastmail-cli chose `~/.config` on all platforms for consistency. Either is acceptable; the choice matters only for discoverability since no secret lives there.

Repository hygiene: sample configs and tests use obviously fake tokens, and the repository ships no `.env` file. GitHub's secret-scanning provider list does not include Fastmail ([GitHub: Supported secret scanning patterns](https://docs.github.com/en/code-security/reference/secret-security/supported-secret-scanning-patterns)), so a leaked Fastmail token in a public commit would not be auto-revoked; the only remedy is manual removal in Fastmail (section 8). A pre-commit grep for the `fmu1-` token prefix seen in fastmail-cli's example (`api_token = "fmu1-..."`, [fastmail-cli README](https://github.com/radiosilence/fastmail-cli/blob/main/README.md)) is cheap insurance; the prefix is observed, not documented by Fastmail, so the check is advisory.

## 8. Revocation and authentication failure

Observed on 2026-10-14: `GET https://api.fastmail.com/jmap/session` with an invalid bearer token, or with no Authorization header, returns `HTTP/2 401` with `www-authenticate: Bearer resource_metadata="https://api.fastmail.com/.well-known/oauth-protected-resource/jmap/session"` and a `text/plain` body (direct `curl -D -` against the endpoint). RFC 6750 §3.1 defines this as `invalid_token`: "The access token provided is expired, revoked, malformed, or invalid for other reasons", and the client "may request a new token" ([RFC 6750 §3.1](https://www.rfc-editor.org/rfc/rfc6750.html#section-3.1)). RFC 9110: "If the request included authentication credentials, then the 401 response indicates that authorization has been refused" ([RFC 9110 §15.5.2](https://www.rfc-editor.org/rfc/rfc9110.html#name-401-unauthorized)); for 403 "the client SHOULD NOT automatically repeat the request with the same credentials" ([RFC 9110 §15.5.4](https://www.rfc-editor.org/rfc/rfc9110.html#name-403-forbidden)). JMAP's own request-level error types (`unknownCapability`, `notJSON`, `notRequest`, `limit`) do not cover authentication; a 401 is an HTTP-level refusal ([RFC 8620 §3.6.1](https://www.rfc-editor.org/rfc/rfc8620.html#section-3.6.1)).

A revoked token therefore looks identical to a bad one: 401 on the session fetch and on every later call. On 401 sift must: stop (no automatic retry with the same token, no retry loop in a push or poll task), tell the user the token was rejected and may have been removed in Fastmail, offer to run setup again, and on re-setup overwrite the keychain item with the new token. The old token is already dead at Fastmail, so there is nothing to revoke from sift's side, and sift cannot revoke a token (removal is a Settings action only; the `/oauth/revoke` endpoint on the dev page is for OAuth tokens, [fastmail.com/dev](https://www.fastmail.com/dev/)). If the user suspects a leak, the action is in Fastmail: open the token, Remove access, and generate a new one; the token screen also shows last-used time, which is the only audit signal available ([Fastmail help: API tokens](https://www.fastmail.help/hc/en-us/articles/5254602856719-API-tokens)). A `sift logout` (or `--forget-token`) command that calls `delete_credential()` lets the user clear the local copy; `NoEntry` on that path is success.

Startup when no token exists: keyring returns `NoEntry`; sift runs setup, reads the token from a terminal prompt (echo off) or from stdin when not a terminal, validates it against the session resource, checks the session's capabilities contain `urn:ietf:params:jmap:mail`, and only then writes the keychain item. `NoStorageAccess` (locked keychain) and the prompt's Deny are reported as such, not as "wrong token".

## 9. Standard

1. The token is a secret from the moment it enters the process. It is held only in a `secrecy::SecretString`; `expose_secret()` is called in exactly one function, the one that builds the `Authorization` header. No other type stores the token as `String`, `&str`, or `Vec<u8>`.
2. The primary store is the macOS login keychain, as a generic-password item with service `sift` and account set to the Fastmail username, written and read through `keyring-core` with `apple-native-keyring-store` (`keychain` feature only) or, equivalently, `security-framework`'s generic-password functions. No other store is written.
3. The config file never contains the token. Sample configs, tests, fixtures, and documentation use obviously fake values.
4. `SIFT_API_TOKEN` overrides the keychain when set. It exists for CI and scripted dry runs; it is read once at startup with `std::env::var`, moved into `SecretString`, and never written back to the keychain or any file. If declared through clap, `hide_env_values(true)` is set. The token is never accepted as a command-line argument.
5. A token used from CI is a separate token, scoped Read-only unless the job must mutate, stored as a CI secret and passed only through the environment.
6. The token's Fastmail scope is Email only. Not Read-only, not Email submission, not Contacts, not Masked Email. At startup sift checks that the session's capabilities include `urn:ietf:params:jmap:mail` and fails with a fixed message naming the required scope if not.
7. Setup reads the token from a terminal prompt with echo off, or from stdin when stdin is not a terminal, validates it against `/jmap/session`, and only then stores it.
8. The `Authorization` header value is marked sensitive (`HeaderValue::set_sensitive(true)`, which `reqwest::RequestBuilder::bearer_auth` does). No code logs raw request or response headers or bytes.
9. Nothing formats the token: no `Debug` or `Display` on any struct holding it (the `SecretString` wrapper enforces this), no `#[instrument]` argument that is the exposed string, no error type that carries it, no panic message that includes it, no serde `Serialize` on a type that holds it. The dry-run log records thread ids and actions only.
10. An HTTP 401 is fatal for the session: no retry with the same token, the UI reports that the token was rejected or removed and offers setup again, and re-setup overwrites the keychain item. 403 is reported as insufficient scope with no retry.
11. `sift logout` (name to be set by the spec) deletes the keychain item; `NoEntry` is treated as success. Revoking the token at Fastmail is a manual Settings action and the docs say so.
12. If a secret-bearing file is ever added (none is planned), it is created with mode 0600 inside a 0700 directory, written to a temp file and renamed into place, and refused if the path is a symlink.
13. A rebuilt dev binary is a new app to the keychain ACL and will prompt once; the docs tell developers this is expected, to click Allow, and that a stable self-signed code-signing identity removes the prompt.
